# Changelog

All notable changes to MTL5 are documented in this file.
Format follows [Conventional Commits](https://www.conventionalcommits.org/).

## [Unreleased]

### Added

- **The thread pool is public API: `mtl::parallel::thread_pool`, with `pool()` and `configure()`** (#630). Code built on MTL5, such as synapse's quantized matmul and attention kernels, can run its parallel work on the pool MTL5's own kernels use, and so share one set of workers instead of oversubscribing the cores. The header is `<mtl/parallel/thread_pool.hpp>`, and its contract is documented there and in `docs/algorithms/on-node-threading.md`:
  - the caller runs tid 0, and `run` blocks until every tid completes;
  - every task's writes happen-before the caller's next action;
  - nested or concurrent regions run serially.

  `mtl::detail::thread_pool` and `<mtl/detail/thread_pool.hpp>` remain as aliases, so existing callers compile unchanged.
  - **`run()` and `parallel_for()` no longer allocate**, whatever the task captures. The task used to be copied into a `std::function`, once by `run` and again by each worker. That was allocation-free only while the wrapping lambda fitted the standard library's small buffer, which the standard does not promise. The pool now holds a pointer to the caller's callable plus a function pointer. A test replaces global `operator new` to check this with a 256-byte capture. `parallel_reduce` and `parallel_accumulate` still allocate their per-chunk partials, and are documented as doing so.
  - **`configure(threads)`** sizes the pool from code. It applies only before the pool's first use, overrides `MTL5_NUM_THREADS`, is clamped to the hardware concurrency in the same way, and returns `false` once the pool exists. Before this, an application had to `setenv` before first use.
  - **A per-call team cap.** `parallel_for`, `parallel_reduce` and `parallel_accumulate` take `max_threads` before the body (`0`: the whole pool), so a caller can run below the pool's size without partitioning by hand through `run`. The existing signatures and their behaviour are unchanged.
  - A real-time variant, with mutex-free dispatch and a spin-then-futex wait, is #636.
- **One thread pool across shared libraries: `MTL5::shared_pool`** (#639). Header-only MTL5 gives each shared object built with `-fvisibility=hidden` and each Windows DLL its own copy of the pool. Python extension modules built with nanobind or pybind11 are built that way, so two such modules in one process started two pools. Each pool was sized from `MTL5_NUM_THREADS`, and `configure()` reached only one of them.
  - The new CMake option `MTL5_SHARED_POOL_LIBRARY` (default off) builds and installs `mtl5_pool`, a small shared library that holds the process's one pool. Modules that link `MTL5::shared_pool` get `MTL5_SHARED_POOL` defined. Their `pool()` and `configure()` then use that pool, looked up once per module, so `run()` stays inline.
  - `<mtl/parallel/shared_pool_definition.hpp>` provides the same definition for builds that do not use MTL5's CMake.
  - The exported functions carry a layout version (`_v1`), so a module built against an incompatible pool header fails to link.
  - A test loads two hidden-visibility modules, which are DLLs on Windows, and checks that they and the executable share one pool, its configuration and its busy state. A third module, built without the macro, shows that it keeps a pool of its own.
  - The default header-only build is unchanged.

- **A vendor BLAS called inside an MTL5 parallel region runs on one thread** (#640, #645). A region thread that calls MKL or BLIS used to have that library start a full team of its own, so an 8-thread region ran 64 threads on 8 cores. The BLAS and LAPACK wrappers and the CHOLMOD/SPQR calls now limit the vendor to one thread on region threads, once per region, and restore the caller's setting when the region ends. Calls made outside a region keep the vendor's threads.
  - **Which vendors:** configure identifies the linked vendor from its exported symbols. MKL is capped with its thread-local `MKL_Set_Num_Threads_Local`. BLIS is capped only where configure measures its thread setting to be per-thread (BLIS 1.0 and later; BLIS 0.9's setting is process-wide), and the status line says which. CHOLMOD's `nthreads_max` and SPQR's `SPQR_nthreads` are capped where `cholmod_common` has them.
  - **OpenBLAS is not capped**: its only setting is process-wide, so capping it in a region would also serialize direct calls. `docs/algorithms/on-node-threading.md` describes the two working setups, either MTL5 threaded with `OPENBLAS_NUM_THREADS=1` or OpenBLAS threaded with MTL5 at one thread.
  - **Measured** (i7-12700K, 64 dgemms in an 8-thread region, vendor team 8, median of 3 rounds, `benchmarks/bench_vendor_nested.cpp`): BLIS 1.1 goes from 0.1 / 0.6 / 3.0 to 405 / 457 / 507 GFLOP/s at n = 128 / 256 / 512, and MKL 2026.1 goes from 328 / 338 / 381 to 499 / 468 / 513. OpenBLAS uncapped is erratic (102–407 across rounds); at one process-wide thread it holds 462 / 430 / 486.
  - New in `<mtl/parallel/thread_pool.hpp>`: `detail::in_region()` and `detail::on_pool_worker()`, shared across modules under `MTL5::shared_pool`. CI gains a BLIS lane on `ubuntu-26.04`.

- **Arduino Ventuno Q benchmark profiles** (#642, #644): a blocking A/B profile pinned to the board's Cortex-A78C cores (found from `/proc/cpuinfo` rather than assumed), and register-tile sweep profiles for the Ventuno Q, the Jetson Orin Nano and the Ryzen 9 8945HS. `MTL5_GEMM_MR_OVERRIDE=<n>` sets `mr` alone so a sweep holds the cache blocks fixed.

### Changed

- **The NEON GEMM register tile grows from 6 × nr to 8 × nr** (#643, #644): 8×4 for fp64 and 8×8 for fp32 on aarch64. AVX-512 keeps 6×16. The tile derivation had assumed AVX2's 16 vector registers on every ISA; `hw_traits` gains `acc_vectors`, and aarch64 now gets 32 registers with a 16-accumulator budget.
  - **Measured** on the Ventuno Q (4× Cortex-A78C, `mr` swept at fixed nr/kc/mc/nc, geomean ratio to `mr = 6`): fp64 8×4 is 1.174× at T=1 and 1.102× at T=4, and no shape is below 1.06. fp32 8×8 is 1.170× and 1.219×. Single-core fp64 goes from 8.3 to 9.7 GFLOP/s, 57% of peak.
  - **Why not 3/4 of the register file:** 12×4 would have regressed T=4 by up to 16%. On the 64-row shapes, each of four threads gets a 16-row block, which 8-row panels tile exactly and 12-row panels cover with 24 rows of work.
  - **AVX-512 is unchanged** because no tile cleared a 5–40% round-to-round spread on Zen 4 under WSL2. The Jetson and other aarch64 cores also move with this change and are not yet measured. `MTL5_GEMM_TARGET_REGISTER_FILE` (the rejected 3/4 candidate) and a `tile6` arm remain measurable.

### Fixed

- **`ldlt_factor` no longer reports a zero pivot that `ldlt_bk_factor` and `cholesky_factor` don't see** (#421). Its default path formed each diagonal term as `(L(j,k) * L(j,k)) * D(k)`: the square of an already-rounded multiplier, scaled afterwards. On an SPD float matrix whose Schur complement is under 2 ulps of the diagonal, that landed exactly on `A(j,j)` and returned `j + 1`, while `ldlt_bk_factor` factored the same matrix without an interchange. The default paths of `ldlt_factor` and `ldlt_h_factor` now do what their comment always described: form `v(k) = L(j,k) * D(k)` (conjugated for LDLᴴ) once per column, and subtract `L(·,k) * v(k)`. That is the association `ldlt_bk_factor` and the accumulator kernel already use, and it saves a multiply per inner-loop term.
  - **Results change in the last bits** for float and double input to the default path, since the products round differently. A matrix that factored before still factors, except possibly one sitting on a pivot that is zero to rounding either way. The accumulator paths (`ldlt_factor<Acc>`) are unchanged, and the default path's `D` now matches `ldlt_factor<T>`'s bit for bit (`L` still sums before subtracting, as before).
  - The issue's own caveat stands: this changes a one-rounding coin flip on pivots within a couple of ulps of zero. Further into ill-conditioning, no association helps.
- **GEMM with an empty dimension passed a leading dimension of 0 to BLAS** (#645). BLIS rejects that ("parameter number 10 had an illegal value") and leaves C untouched, so `mult` with k = 0 did not zero C under BLIS. Every leading dimension is now at least 1.
- **`analyze_blocking_ab.py` called a null run a match** (#642). On a board whose kernel lists cache levels without sizes, every detecting arm fell back to the compile-time model, and the analyzer reported "its caches already match the compile-time model". It now says that detection found nothing.
- **Highway's CMP0111 deprecation warning** no longer prints on every configure with `MTL5_WITH_HIGHWAY=ON` (#642).

## [5.20.0] - 2026-10-22

Block-quantized data becomes a first-class operand. `mat::block_matrix_view` is a read-only `Matrix` over the encoded bytes of a block-quantized format, parameterized by the new `BlockScheme` concept, with the OCP MXINT8 and MXFP4 schemes in-tree (#629). A scheme can plug in a fused gemv whose working memory the caller supplies. `simd::reduce_dot_block_scaled` is the inner-product kernel such formats need: each block's exact integer sum is scaled in-register, with one horizontal reduce per call (#628). The threaded GEMM now chooses its ic step by micro-panels, 3–16% faster on the configurations it changes, measured on three machines, and slower on none (#458).

Everything new is additive. The GEMM change alters only how rows are split into blocks, not the order of any sum.

### Added

- **`mat::block_matrix_view`: a read-only `Matrix` over block-quantized storage** (#629), parameterized by the new **`BlockScheme`** concept: block geometry (`block_size`, `block_bytes`) plus a reference `decode` of one block's raw bytes, and optionally `decode_element`. The view is non-owning (typically over a memory map), row-major with blocks along rows, and read-only, and its constructor checks the shape. Elements read as decoded `float`; `block(r, b)` and `row(r)` expose the encoded bytes.
  - **Operations:** `convert` to a dense matrix and `mult(A, x, y)` / `A * x` decode a row at a time, threaded over rows and independent of the thread count. A scheme can plug in a fused gemv by specializing `mtl::block_kernels<S>`, which `mult` uses for contiguous `float` vectors with no explicit `Accumulator`. The kernel's working memory (typically the quantized `x`) is the caller's: `mult(A, x, y, scratch)` passes it through, sized and aligned by `block_gemv_scratch_bytes<S>` and `block_gemv_scratch_alignment<S>`, and `mult(A, x, y)` allocates it for the call.
  - **In-tree OCP MX schemes**, Universal-free: `mx::mxint8` (E8M0 scale plus 32 × INT8, q/64) and `mx::mxfp4` (E8M0 plus 32 × FP4 E2M1, in GGML's `block_mxfp4` nibble order, so gpt-oss GGUF data can be viewed in place). A scale of 0xFF is NaN. Under the largest scale, elements of magnitude 2 or more decode to infinity, since they exceed float's range.
  - Design notes: `docs/architecture/containers/block-matrix-view-architecture.md`. The encode direction (quantizing activations into a block format) is a follow-up.

- **`simd::reduce_dot_block_scaled`: block-scaled integer dot products** (#628). Computes `Σ_b scales[b] · Σ_{j∈b} a_j·x_j` over consecutive blocks, the inner product of block-quantized formats (GGML Q4_0/Q8_0/Q4_K/Q6_K, OCP MXINT8, 16-wide NVIDIA-style blocks), with the caller supplying decoded float scales. Each block's exact integer sum stays in vector lanes and is converted and scaled in-register, with one horizontal reduce per call instead of one per block. It takes `reduce_dot_widen`'s operand pairs, and blocks of any length; the part that isn't a multiple of the SIMD step is summed as a scalar.
  - **Contract:** each block's integer total is exact. Lane partial sums are converted and accumulated in float in an order fixed by block index, so the result is reproducible run to run on one target and equals the per-block loop up to float re-association across targets. Overflow is a per-block precondition (`Σ |a_j·x_j| < 2³¹`, or 2³² for the unsigned pairs), not "the sum wraps".
  - **New primitive:** `batch<float>::convert` from `int32_t` and `uint32_t` lanes, rounding as `static_cast` does. `widen_dot_accumulate` and `quad_dot_accumulate` are now documented as public building blocks for this pattern.
  - **Measured** (i7-12700K, AVX2, single thread, `benchmarks/bench_block_scaled_dot.cpp`): at block 32 it is 1.3–1.4× faster than one `reduce_dot_widen` per block in cache, and 1.15–1.4× faster at 4096×4096; at block 256 the two match. The numbers and their limits are in `docs/algorithms/mixed-precision-kernels.md`.

- **`#458` before/after profiles** `benchmarks/machines/{xeon-e5-2420,i7-12700k,ryzen-9-8945hs}-mc.sh` and a `legacymc` benchmark arm, with the three machines' data under `benchmarks/data/*-mc458`.

### Changed

- **The threaded GEMM chooses its ic step by micro-panels** (#458, #626). The serial path rounded `mc` down to whole `mr`-row panels; the threaded path rounded the ic block count up to a multiple of the thread count and kept whatever `mc` came out, so every block carried a padded partial panel. The Xeon's shipped threaded `mc = 32` against `mr = 6` ran 5.33 panels padded to 6. This is what made #458's multi-threaded `mc` curve W-shaped. The busiest thread's panel count fits that curve at r = +0.83; the block-count balance `balanced_mc` optimised fits at +0.23.
  - **Rule:** in the threaded path, `balanced_mc` keeps the block-count result unless a block size in `[ceil(mc_max/2), mc_max]` gives the busiest thread strictly fewer panels (new `detail::critical_panels`, closed form). Ties keep the old plan; the window stops it shrinking blocks into extra passes over packed B. The serial path, the #488 sub-tile fallback and `mr = 1` callers are unchanged. `MTL5_GEMM_LEGACY_BALANCED_MC` restores the old rule for diagnosis.
  - **Measured** (pinned, 4 interleaved rounds against the old rule built from the same tree): Xeon E5-2420 v2 all 16 changed plans faster by 7.5–16.2%, 2048³ T=6 45.3 → 52.6 GF/s; i7-12700K 12 of 13 faster by 3.1–9.2%; Ryzen 9 8945HS (Zen 4, WSL2) all 5 faster by 3.4–6.4%. None slower on any machine; T=1 unchanged everywhere. See `docs/performance/mc-critical-panels.md`.

### Fixed

- **`run_blocking_ab.sh` called `default` and `legacymc` a consistency pair** (#626). It compared configured kc/mc only; it now also keys on every row's `mc_used`. It also refuses an arm CSV with no complete data record, which previously compared equal to another empty one.

## [5.19.0] - 2026-10-20

The accumulator policy now reaches every reduction-bearing routine in the library (#585): the dense direct factorizations, Bunch–Kaufman, the four incomplete-factorization preconditioners, `spgemm`, `svd`, `sum` and `trace`, the sparse eigensolvers, and the multigrid transfers and cycle. Accumulator-typed `dot` and norms run on the thread pool through `merge`, and the accumulator GEMM is up to 23× faster. Three new accumulation tools join plain and FMA:
- `math::exact_accumulator<T>`, an in-library Kulisch accumulator for `float` and `double`;
- Ogita, Rump and Oishi's compensated Sum2/Dot2 as `compensated_accumulator<T>` (configuration 2c);
- their K-fold `sum_k` / `dot_k`, built on new error-free transformations.

The configuration 1/2/2c/3 accumulation matrix (#586) is measured, tested and published. Two preconditioner bugs are fixed, and matrix-free operators work in the Krylov solvers again.

Every new `Accumulator` parameter defaults to `void`, which runs exactly the code 5.18.0 ran. Three behaviour changes affect only callers who pass an accumulator explicitly; see Changed.

### Added

- **Accumulator policy for the dense direct factorizations** (#594, #595, #585). `lu_factor`, `lu_solve`, `lu_adjoint_solve`, `lu_apply`, `inv`, `cholesky_factor`/`_solve`, `cholesky_h_factor`/`_solve`, `ldlt_factor`/`_solve`, `ldlt_h_factor`/`_solve`, `ldlt_bk_factor` and `ldlt_bk_solve` take a leading `Accumulator = void`. A non-void accumulator skips LAPACK (`interface::accumulator_allows_blas_v`).
  - **LU and Bunch–Kaufman change loop order for it.** Their `void` factorizations are right-looking, where an entry is updated once per step and there is no single sum to hold. The accumulator paths are left-looking: Doolittle for LU, and a Bunch–Kaufman that forms each Schur column on demand from W = L·D. Each entry of the factor is one reduction, rounded once. Pivoting, storage and the `ipiv` encoding are the same as the `void` path's, so either solve reads either factor. The tests mix the factor of one path with the solve of the other.
  - **Solves form `b(i) − Σ` inside the accumulator** and round once before the division. Rounding the sum first, as `lower_trisolve` does, gave away the whole gain: every configuration landed near 1e-8.
  - **Effect** (float Hilbert(n), exact relative residuals; plain / fma / exact): LU n = 8 gives 2.8e-8 / 1.3e-8 / 2.9e-9, and `inv` n = 8 gives 1.7e-1 / 6.9e-1 / 3.8e-3. Cholesky of Hilbert(9) factors only with the exact accumulator.
  - **Cost:** the accumulator paths of LU and Bunch–Kaufman store an n × n workspace; see `docs/architecture/accuracy-architecture.md` §2.
- **Accumulator policy for the incomplete-factorization preconditioners** (#597, #598, #600, #603). `pc::ilu_0`, `pc::ic_0`, `pc::ilut` and `pc::ildl` take a trailing `Accumulator = void`, the class-template convention `pc::ssor` set.
  - **Factorizations:** ILU(0) and ILUT keep one accumulator per live entry of the row being eliminated. IC(0) and ILDL are already up-looking, so each entry is one reduction.
  - **Solves:** they form `b − Σ` in the accumulator. The adjoint and Lᵀ solves scatter into n accumulators, which is O(nnz), where the `void` path scans later rows.
  - **ILUT drop tests** read the single-rounded values, so with dropping, a different accumulator can keep a different pattern.
  - **Finding:** the length of the reductions decides whether an exact accumulator helps. On stencil patterns all configurations agree. On a dense pattern, where IC(0) and ILU(0) are Cholesky and LU, exact is 2–4× better at least. At Hilbert(9), IC(0) breaks down to NaN under plain and FMA but not under exact.
- **Accumulator policy for `spgemm`** (#604). A leading `Accumulator = void`, with one accumulator per touched column of the current row, mapped through a slot table so that at most nnz(C row i) are live. The pattern is unchanged.
  - With the exact accumulator every entry is correctly rounded. On a 40×60 · 60×40 cancelling product, plain misses at 584 of 1589 entries, FMA at 446 and exact at none.
  - A plain element-type accumulator gives the `void` bits, except that an entry whose only nonzero contribution is a −0 product comes back +0.
- **Accumulator policy for `svd` and `null_vector`** (#606). Every overload takes a leading `Accumulator = void`. It covers:
  - the one-sided Jacobi inner products, raw and scaled;
  - the Gram–Schmidt completion of U;
  - the Householder QR preconditioner and U's reflector back-application.

  The plane rotations stay in `value_type`, and a non-void accumulator skips `gesdd` and `geqrf`. The finding is no ordering: Jacobi's error comes from applying the rotations, not from the inner products that choose them.
- **Accumulator policy for `sum` and `trace`** (#607). Each element goes through `add_product(acc, x, 1)`, which is exact for every number system, so the protocol needs no `add` primitive. For a plain sum, configurations 1 and 2 are therefore bit-identical. The exact accumulator returns the correctly rounded sum.
- **Accumulator policy for the sparse eigensolvers** (#605). `sparse_eigs` and `sparse_eigs_shift_invert` take a leading `Accumulator`, and `shift_invert_operator` takes a trailing one. It reaches:
  - the LU factorization of A − σI and every solve that applies it;
  - Arnoldi's inner products;
  - for `sparse_eigs`, the matvec through `mult<Accumulator>`.
- **Accumulator policy for multigrid** (#608). `restrict` and `prolongate` take a leading `Accumulator`, and `multigrid<Value, Accumulator>` passes it to both transfers in the V- and W-cycles and to the cycle residual `r = b − A·x`, formed in the `b − Σ` shape. Smoothers remain the caller's choice (`smoother::*<Matrix, Accumulator>`). This completes #585.
- **Accumulator-typed reductions run on the thread pool** (#584). `dot`, `dot_real`, `two_norm` and `frobenius_norm` with an explicit `Accumulator` split across `thread_pool` when `mergeable_accumulator<Acc, Value>` holds, combining partials with `accumulator_traits::merge` (5.18.0) in chunk order.
  - **Determinism:** an exact accumulator gives the serial bits at every thread count. For a posit⟨32,2⟩ quire over 2²⁰ elements it went from 830 ms on one thread to 125 ms on eight, with identical bits.
  - Accumulators without a `merge`, and non-dense operands, stay serial. The new `detail::parallel_accumulate` and `detail::accumulate` carry it.
- **`math::exact_accumulator<T>`** (#612, #611), in `include/mtl/math/exact_accumulator.hpp`. The test-only Kulisch accumulator of #589 moves into the library: an exact sum of products of `float` or `double`, rounded once to nearest-even, with subnormals and overflow handled. Each object is 88 bytes for float and 544 for double: 10 or 67 64-bit limbs plus a non-finite flag.
  - **Non-finite inputs follow IEEE**, kept apart from the finite sum.
  - **Operand types:** `V` must be exactly representable in `T`. `long double` is excluded.
  - **Integration:** it plugs in through the ADL hook, so every accumulator-aware operation takes it, and its `merge` is exact.
  - **Docs:** `docs/architecture/exact-accumulator.md`.
- **Error-free transformations** (#614), in `include/mtl/math/error_free.hpp`: `two_sum`, `fast_two_sum`, Veltkamp `split`, `two_product_dekker` (exact up to `max` by rescaling) and `two_product` (FMA, moved from `accumulator_traits.hpp`, which includes the new header; `split_product` is kept as an alias). Each returns `exact_pair<T>{hi, lo}`.
  - `split` and `two_product_dekker` switch FP contraction off locally, since GCC's `-ffp-contract=fast` otherwise turns `split` into `(a, 0)` on any FMA target. Their test is built with `-ffp-contract=fast` so the ARM64 runners exercise the guard.
  - `-ffast-math` is unsupported. See `docs/architecture/error-free-transformations.md`.
- **`math::compensated_accumulator<T>`, configuration 2c** (#615). This is Ogita–Rump–Oishi Sum2/Dot2 as an accumulator, holding two `T`s. The result is as accurate as twice the working precision, rounded once. `mtl::dot` with it gives the bits of the paper's Dot2 loop.
  - **Merge** stays within the bound but is not bit-identical across thread counts.
  - **Accuracy:** on GenDot in double it stays at exact's level up to cond ≈ 1e16 and then grows as u²·cond.
- **`sum_k<K>(x)` and `dot_k<K>(x, y)`** (#616), in `include/mtl/operation/sum_dot_k.hpp`: Ogita–Rump–Oishi SumK and DotK. Each returns the sum or dot product as if computed in K-fold precision, then rounded once. `sum_k<2>` and `dot_k<2>` give the same bits as `compensated_accumulator`. They take whole vectors, since they keep n or 2n error terms.
- **Exact three-factor terms in the LDLᵀ accumulator paths** (#609, #610, #602). `add_product` takes two factors, so the `L·d` of each `L(i,k)·d_k·L(j,k)` was rounded before the accumulator saw it. A new trait, `math::splits_product_terms_v<Acc, Value>`, marks when that rounding error is worth recovering. When it holds, the kernels also pass `two_product`'s `lo`, so the whole term reaches the accumulator. Over 300 perturbed Hilbert matrices this adds 1.1–1.6×, and dense LDLᵀ, sparse LDLᵀ and ILDL now order exact below plain and FMA.
  - **Paths changed:** dense `ldlt_factor`/`ldlt_h_factor`, `ildl`, `sparse_ldlt_numeric` and `supernodal_ldlt_numeric`. Bunch–Kaufman feeds stored Schur columns and is unaffected.
  - **Trait coverage:** it holds for an IEEE `Value` with an ADL accumulator, the compensated accumulator, or a strictly wider built-in float.
  - **Perf:** #610 forms the supernodal split coefficients once per update column, with identical bits.
- **`generators::gen_dot` and `gen_sum`** (#617), in `include/mtl/generators/ill_conditioned.hpp`: the Ogita–Rump–Oishi Algorithm 6.1 GenDot and its derived ill-conditioned sums. `exact_accumulator` serves as the paper's `DotExact`. Each returns the exact result rounded to nearest and the achieved condition number. A seed reproduces the same vectors with any standard library. See `docs/generators/ill-conditioned.md`.
- **`examples/accurate_sum_dot`** (#619, #620) reproduces Section 6 of Ogita, Rump and Oishi:
  - Figures 6.1–6.4, with an added float run;
  - Table 6.2, correct digits;
  - Tables 6.4–6.5, timings.

  Errors are measured exactly, and no proven bound is violated on 3000 dot products under GCC or Clang. `docs/examples/accurate-sum-dot.md` plots the results beside the paper's.
- **Tests for the accumulation matrix** (#589, #590, #622). The configuration 1/2/2c/3 matrix covers dot, gemm, norms, the direct solvers, refinement, Krylov, eigen, the preconditioners, `spgemm`, `sum` and `svd`, plus determinism. The rows are tagged `[586:*]` so the peer repos' quire rows can name them.
  - **Theorem tests:** `test_ogita_rump_oishi` asserts the paper's numbered bounds as inequalities on every GenDot/GenSum instance (#618).
  - **Portability:** #622 fixed undefined seed conversions and unspecified argument evaluation order, so GCC, Clang and MSVC now draw the same random inputs.

### Changed

- **A non-void `Accumulator` now reaches the eigensolvers' matrix-vector product** (#593, #591). `power_iteration`, `lanczos` and `arnoldi` take a leading `Accumulator`. When `A` is a `Matrix`, `ev_matvec` now forms `w` with `mult<Accumulator>`, as the Krylov solvers do; before, the accumulator covered only the dot products.
  - Results change for callers who pass one. On a float matrix whose matvec cancels by four orders of magnitude, `power_iteration` with the exact accumulator now converges, to 8.0e-6, where all configurations previously stalled at 5.4e-3.
  - `void` and matrix-free operators keep `A * x`, byte-identical.
- **Threaded accumulator reductions regroup by chunk** (#584). With `MTL5_NUM_THREADS` > 1, a rounding accumulator such as a wider type or `fma_accumulator` in `dot`, `dot_real`, `two_norm` or `frobenius_norm` now gives bits that depend on the thread count. This is the contract the threaded `float`/`double` reductions already have. With one thread, the default, nothing changes; exact accumulators are unaffected.
- **LDLᵀ results with exact, compensated or wider accumulators change** (#609): they now see whole three-factor terms. `void`, plain, `fma_accumulator`, complex, non-IEEE types, and accumulators with a direct `accumulator_traits` specialization give the 5.18.0 bits.
- **The accumulator GEMM is 5–23× faster** (#588). `mult<Acc>(A, B, C)` packs B into k-major column panels and keeps one accumulator per column, so the k loop is unit-stride. At n = 1024: 23× for `double`/plain, 4.6× for `fma_accumulator` and 8–15× for `float` into a `double` accumulator.
  - **Bits:** each entry gets the same terms in the same order, so results are bit-identical under `-ffp-contract=off`. Under FMA contraction the new kernel may fuse where the old one didn't on GCC.
  - **Gate:** software element types such as posits, and large accumulators such as quires, keep the dot-product loop.
- **`itl::idr_s` accepts any linear operator** (#624): its `Matrix LinearOp` constraint is now `typename`, like the other Krylov solvers.

### Fixed

- **Matrix-free operators compile in the Krylov solvers again** (#624, #278). The accumulator rollout (#254) moved every matvec to `mult<Accumulator>`, which requires a `Matrix`, so an operator with only `operator*` stopped compiling in all ten solvers.
  - **Fix:** the new `itl::apply_operator` and `apply_transpose` (in `itl/krylov/apply_operator.hpp`) send a `Matrix` through `mult<Accumulator>` exactly as before, and apply anything else as `A * x`. `bicg` and `qmr` use a matrix-free `trans(A)` found by ADL.
  - **Accumulator contract:** a non-void accumulator reaches only the dot products around a matrix-free operator, the contract `ev_matvec` has.
  - **Tests:** all ten solvers run on a matrix-free operator and are bit-identical to the stored-matrix solve. A lazy-product case runs `apply_transpose` past a temporary `trans(A)`; it fails under AddressSanitizer without the lifetime fix.
- **`pc::ilut` back substitution counted the diagonal twice** (#599). This is the #323 bug `ilu_0` once had. The diagonal was stored in the U rows and divided by again, which is wrong for every input: a no-drop ILUT, which is an exact LU, gave `(Ax)(0) = −3` for `b(0) = 1`. The diagonal now lives only in `u_diag_`.
- **`pc::ilut::adjoint_solve` applied M⁻¹ instead of M⁻ᴴ** (#599), the #394 defect. ILUT of a symmetric A is not symmetric, so even there the adjoint identity failed, by 1.6e-3. It now has a real scatter-form adjoint.
- **`pc::ic_0` and `pc::ildl` `adjoint_solve` applied M⁻¹ for complex values** (#601). Both factor L·Lᵀ (L·D·Lᵀ) without conjugation, so a complex `Value` models a complex symmetric matrix, whose adjoint is conj(M), not M. The adjoint identity was off by up to 1.2. `solve` and `adjoint_solve` now share `apply<Conj>`, and real types are byte-identical.
- **The multigrid transfers started their sums from `Value{}`** (#608), which is 1, not 0, for an LNS type. They start from `math::zero<Value>()`, byte-identical for built-in types.

### CI

## [5.18.0] - 2026-10-16

A Universal quire is now an accumulator for any MTL5 operation that takes one, with no bridge header in between. `accumulator_traits` forwards to free functions defined next to the accumulator type, which Universal 5.7.0 provides for its quire. The trait also gains `merge`, the combine step a parallel reduction needs. Nothing changes for existing accumulators: plain and `fma_accumulator` behave as before, and an explicit `accumulator_traits` specialization still takes precedence. Two design documents compare MTL5 with Elemental.

### Added

- **Super-accumulators plug into `accumulator_traits` through free functions found by argument-dependent lookup** (#581, #582). When an accumulator's own namespace provides `accumulator_clear`, `accumulator_assign`, `accumulator_add_product` and `accumulator_value(acc, std::type_identity<R>{})`, the `adl_accumulator` concept is satisfied and a constrained specialization forwards each operation to them. `accumulator_merge` is optional.
  - **Why:** the Universal quire's specialization was a header, `quire_accumulator.hpp`, copied byte for byte into mp-blas, mp-ir, mp-iterative and mp-numerics, with diverged copies in mp-spice and mtl5-python. It specialized MTL5's trait, so it had to include MTL5 and couldn't live in Universal. Now Universal defines the functions beside `quire` (universal#1699, in 5.7.0) without including MTL5, and MTL5 only names them, so it stays Universal-free. `dot<quire<P>, P>(x, y)` and `sparse_lu_solve<quire<P>>(A, x, b)` work with Universal 5.7.0 and nothing else. The mp-* repos have deleted their copies; mtl5-python can once it pins this release.
  - **Precedence:** a specialization that names the accumulator type is more specialized than the constrained one, so an existing bridge keeps compiling and keeps being used until it is deleted.
  - **Naming:** `accumulator_value` takes a `std::type_identity<R>` tag rather than an explicit template argument, so the call is an ordinary ADL call on every compiler. The hook functions should be constrained on the accumulator type, since ADL also searches the namespaces associated with `Value`.
- **`accumulator_traits::merge(a, b)`** combines two partial accumulators of the same reduction: an ordinary add for plain accumulators and `fma_accumulator`, and `accumulator_merge` for an ADL accumulator, which has no `merge()` if it doesn't provide one. For an exact accumulator the combination is exact, so a reduction split across threads or processes gives the same bits however it was split. No kernel uses it yet; letting one accumulator-typed reduction run on `thread_pool` is tracked in #582.
- **Tests:** `test_accumulator_adl_hook` uses a mock exact accumulator in its own namespace. It checks concept satisfaction (configurations 1 and 2 don't satisfy it), forwarding, a 1 − 10⁸ + 10⁸ cancellation that the accumulator keeps exact, `merge` for all three configurations, that a specialization beats the hook, `dot<Acc, Result>`, and all six one-shot sparse direct solvers factoring and solving through the hook.

### Documentation

- **`docs/other/elemental-architecture.md`** (#578) surveys Elemental: the `DistMatrix` distribution algebra, its MPI layer, the closed set of precisions it instantiates, and its maintenance status.
- **`docs/other/mtl5-elemental-assessment.md`** (#580) compares MTL5 with Elemental and proposes a layering. Its recommendation is not to port Elemental. The single-node dense algorithms it has and MTL5 lacks, such as column-pivoted QR, pivoted Cholesky and polar decomposition, belong in MTL5. A distributed layer would be a separate repository depending on MTL5 alone, and is worth building only for reductions that are exact and independent of the process count. Its prerequisites were the ADL hook and `merge` above.

## [5.17.0] - 2026-10-15

A thin SVD and a faster Jacobi core behind every `svd`, and the accumulator policy carried from the sparse direct factorizations into their solves, so a factorization with a wider or exact accumulator no longer ends in a plain rounded triangular solve. One behavior change: the generic `svd`, the V-only `svd` and `null_vector` return different last bits (see Changed); the LAPACK `gesdd` path is unaffected. The new `Accumulator` parameter on the sparse solves defaults to `void`, which returns exactly the bits 5.16.0 did.

### Added

- **Thin SVD: `svd(A, U, s, V)`**, with U m × k, s of length k and V n × k, where k = min(m, n). This is the thin U left out of #566. The full `svd(A, U, S, V)` completes U to an m × m basis, which is almost all of its 0.24 s at 400 × 9.
  - **How:** for a tall A, the generic path reuses the V-only `svd`'s QR preconditioning. It runs one-sided Jacobi on R and forms U = Q [U_R; 0] by applying the n stored Householder reflectors, in O(mn²). For m ≤ n, U, s and V's columns match the first k of the full `svd` bit for bit. With LAPACK, `dense2D<float/double>` goes to `gesdd` in its thin mode, `'S'`, as the full `svd` uses `'A'`.
  - **Speed:** in µs, thin against full `svd`: 13 against 459 at 64 × 9, 49 against 238,000 at 400 × 9, and 85 against 238,000 at 400 × 12. The `null-vector` benchmark suite gains a `svd_thin` arm, whose answer is checked like the others.
  - **Refactor:** U's basis completion moved into `detail::complete_orthonormal`, shared by both overloads. The full `svd`'s arithmetic is unchanged.
  - **Tests:** `test_svd_thin` checks:
    - bit identity with the full `svd` for m ≤ n;
    - agreement to rounding in `long double` on tall shapes up to 400 × 12, including columns graded across 10⁸, with U and V orthonormal, A reconstructed, and the sign of each (uᵢ, vᵢ) pair consistent;
    - `double` against the full `svd` in either build;
    - rank-deficient, zero and empty inputs.

    Skipping the reflectors, applying them in the wrong order, or skipping the completion each fails it.

- **The accumulator policy reaches the solve phase of every sparse direct solver** (#535, #576, #261 Part C). Since 5.13.0 the numeric factorizations have taken an `Accumulator` (#530, #531, #534, #542), but their `solve()` methods summed in plain `Value`, so a factorization done with a wider or exact accumulator still ended in an ordinary rounded triangular solve.
  - **Kernels:** the five level-scheduled triangular solves in `sparse/factorization/level_schedule.hpp` take a leading `Accumulator = void`, the convention #542 set: `level_scheduled_lower_solve<Acc>(L, s, x)`. With `void` they run the original loop. With an accumulator, each row's whole b[i] − Σ T(i,k)·x[k], b[i] included, goes through `accumulator_traits` (`assign`, then `add_product` of the negated terms) and is rounded once before the division by the diagonal. An exact accumulator therefore delivers b − Σ with a single rounding. Each row keeps its own accumulator, so the parallel levels stay race-free and no workspace is added.
  - **Solvers:** `solve<Acc>()` is added to `cholesky_numeric`, `ldlt_numeric`, `lu_numeric`, `supernodal_lu_factor` and `supernodal_ldlt_factor`. `qr_numeric::solve<Acc>` covers its two inline sums, the vₖᵀw dot of Q_hᵀb and the R back-substitution; the latter keeps one accumulator per column, O(ncols), and adds terms in the same order as the default. The one-shot `sparse_{cholesky,ldlt,lu,qr}_solve<Acc>` and `supernodal_{ldlt,lu}_solve<Acc>` pass `Acc` to both the factorization and the solve. With the default `void`, every call returns exactly the bits it did before.
  - **Not covered:** the scatter kernels in `triangular_solve.hpp`, which no solve path calls and which remain the raw reference; `klu_numeric::solve`'s block coupling; and the `*_solve_refined` wrappers, which use the default solve.
  - **Note:** the LU solve uses `mtl::math::accumulator_traits`, as Cholesky, LDLᵀ and QR do. A specialization of only the `sparse::factorization::accumulator_traits` alias is not picked up by `lu_numeric::solve<Acc>`.
  - **Tests:** `test_solve_accumulator_policy` checks:
    - `void` and `Acc == Value` against the `dense_*` references, bit for bit;
    - a `float` row where 1 − 10⁸ + 10⁸ cancels to 0, which gives 1 with a `double` or `fma_accumulator<double>` accumulator, in all five kernels and both QR sums;
    - `solve<Acc>` against the default on every factorization and every one-shot wrapper.

    The bit-identity claim depends on the compiler not contracting `x -= a*b` into an FMA differently in the gather and the scatter, so the target is built with `-ffp-contract=off`, as `trisolve_level_schedule_mt` is (#381). The FP-contract lane found this on the first push.

### Changed

- **The one-sided Jacobi core behind `svd` is 1.3–3.6× faster, and its results change in the last bits.** It is shared by the generic `svd(A, U, S, V)`, the V-only `svd(A, s, V)` and `null_vector`. The LAPACK `gesdd` path is unaffected. Each column pair's inner products ‖b_p‖², ‖b_q‖² and b_p·b_q were formed from entries divided by the pair's largest magnitude, which costs a max pass and 2m divisions per pair, to keep the squares from overflowing or underflowing. They are now summed raw, and kept when ‖b_p‖² and ‖b_q‖² both lie in [√min/ε, √max/2] (about 2^-459 to 2^511 in `double`). Outside that window, which includes any inf or NaN, the sums are re-formed scaled as before. The window also keeps ‖b_p‖²·‖b_q‖² finite and normal, since the convergence test takes its square root. The sweeps also run on column-major copies of B and V, which on its own was about 10% faster with identical bits. A type without a `std::numeric_limits` specialization always takes the scaled path.
  - **Speed:** median µs from `bench_all --suite null-vector`, old core against new, run alternately.

    | m × N | `null_vector` | full `svd` |
    |---|---|---|
    | 16 × 9 | 24 → 6.6 | 46 → 13 |
    | 64 × 9 | 33 → 9.7 | 1,025 → 448 |
    | 400 × 9 | 33 → 27 | 238,000 (unchanged) |
    | 16 × 12 | 27 → 13 | 38 → 18 |
    | 64 × 12 | 31 → 16 | 521 → 452 |
    | 400 × 12 | 62 → 46 | 239,000 (unchanged) |

    At m = 400, QR dominates `null_vector` and the completion of U to m × m dominates the full `svd`.
  - **Accuracy:** on the same inputs the singular values agree with the old core to 1e-15 relative, the sweep counts are the same, and `null_vector`'s `float` accuracy table in `docs/algorithms/eigenvalues.md` is unchanged within noise.
  - **Tests:** a new case in `test_svd` scales a uniform matrix, and one with columns spread from 2^-560 to 2^-80, by 2^k for k from -560 to 520, across both bounds of the window. The singular values must scale by exactly 2^k and V must not move. Removing the lower bound, the upper bound or the scaled fallback each fails it; the upper bound is checked by this test alone.

### Fixed

- **`svd` throws when LAPACK's `gesdd` fails, instead of returning whatever its buffers held.** The LAPACK path of the full `svd(A, U, S, V)` ignored `gesdd`'s `info`, so a NaN in A, which LAPACK 3.10+ rejects with `info = -4`, or a divide-and-conquer that did not converge came back as an apparently valid U, S and V. The full and the new thin `svd` now check `info` after the workspace query and after the decomposition, and throw `std::runtime_error` on a nonzero value, as `eigenvalue` does for `geev`. The generic path is unchanged. A LAPACK-only case in `test_svd_thin` passes a NaN to both and requires the throw; it fails against the previous header. Found by CodeRabbit on #575.

## [5.16.0] - 2026-10-12

Small dense eigen and singular value problems, driven by null-space solves (8-point, DLT, plane fits): a Jacobi eigensolver that keeps small eigenvalues relatively accurate, a V-only SVD with QR preconditioning and `null_vector`, a tighter default tolerance and deflation test for `eigen_symmetric`, and the Householder accumulator forwarded through QR, LQ and the eigensolvers. One behavior change: `eigen_symmetric` and its relatives return different bits by default (see Changed). The full `svd` is bit-identical to 5.15.0.

### Added

- **The Householder accumulator reaches QR, LQ, the Hessenberg reduction and the dense eigensolvers** (#536, #261 Part C). Since 5.13.0, `householder` and `apply_householder_left/right` have taken an `Accumulator` (#537), but none of their callers passed one, so no factorization or eigensolver could use it. `qr_factor`, `qr_extract_Q`, `qr_solve`, `lq_factor`, `lq_extract_Q`, `hessenberg_factor`, `hessenberg`, `tridiagonalize`, `eigenvalue_symmetric_generic`, `eigenvalue_symmetric`, `eigen_symmetric`, `eigenvalue` and `eigen` now take a leading `Accumulator = void`, following #542's convention (`qr_factor<Acc>(A, tau)`), and forward it to every Householder call. `qr_solve` also uses it for the two sums it forms itself: vᴴy when forming Qᴴb, and each row of the back substitution. A non-void accumulator skips the LAPACK dispatch (`geqrf`, `syev` for real and `heev` for complex Hermitian matrices, `geev`), since LAPACK's sums are its own. With the default `void`, every call runs exactly the code it ran before. The QR iterations, the Givens rotations and `eigen`'s inverse iteration keep plain arithmetic: they work on fixed 2- and 3-term expressions or are outside the Householder path. `test_householder_accumulator_callers` counts the accumulator's `add_product` calls in each routine and compares them with the exact number of terms its sums contain, so a caller that drops the accumulator anywhere fails, including a LAPACK build that dispatches instead. A complex Hermitian case covers the `heev` branch, which CodeRabbit found ungated in review. Measured on random 256 × 256 `float` matrices, accumulating in `double` lowers QR's backward error ‖QR − A‖/‖A‖ from 6.8e-7 to 3.7e-7. On the same matrices `qr_solve`'s error and the symmetric eigenvalues' error showed no consistent improvement, since conditioning and the QR iteration dominate them.

- **`eigen_symmetric_jacobi(A)`: a two-sided cyclic Jacobi eigensolver for small dense symmetric matrices** (#564). It returns the same `{eigenvalues, eigenvectors}` as `eigen_symmetric`, eigenvalues ascending. Tridiagonal QR is accurate to about ε‖A‖ in each eigenvalue. For a positive (semi)definite matrix, Jacobi gets small eigenvalues and their eigenvectors to high relative accuracy (Demmel & Veselić), which matters for the null vector of a normal matrix AᵀA. On 9 × 9 and 12 × 12 null-vector problems with columns scaled across 10⁶ (200 trials each), the eigenvector error is 4.9e-15 and 5.4e-15 rad, against 6.6e-7 and 1.9e-6 for `eigen_symmetric`. On graded positive definite matrices whose eigenvalues span 8 to 24 decades, the worst relative eigenvalue error is 6.6e-16, against 2e-13 to 8e-11. It sweeps pairs row by row with the stable rotation t = sign(θ)/(|θ| + √(θ²+1)), formed so θ² cannot overflow. A pair is skipped once |a_pq| ≤ tol·√|a_pp|·√|a_qq|, and the solver stops after a sweep with no rotation. `tol` defaults to ε and `max_sweeps` to 60. The issue proposed stopping on off-diagonal mass ≤ ε²‖A‖²_F instead. That test guarantees only absolute accuracy: it returns diag(1, 1e-10, 2e-10) coupled by 1.5e-16 with the small eigenvalues 2.25e-12 relatively wrong, and a unit test checks that case. No entry is squared, so matrices scaled from 1e+300 down to subnormal values converge. Real element types only, posits included; complex is rejected at compile time. Header `operation/eigenvalue_symmetric_jacobi.hpp`, included from `mtl.hpp`.
  - **Tests:** `test_eigen_symmetric_jacobi` checks:
    - reconstruction and orthogonality for n = 1…16, in `double` and `float`;
    - agreement with `eigen_symmetric`;
    - convergence in under 20 sweeps on 9 × 9 and 12 × 12 normal matrices, by comparing bits with a run capped at 19 sweeps;
    - matrices scaled by 1e±160;
    - relative accuracy against a `long double` reference where `long double` is wider than `double`;
    - zero eigenvalues and trivial sizes.

    Mutating the stop to the Frobenius test, or squaring entries in the pair test, fails the suite.
  - **Benchmark:** a new `bench_all --suite eig-small` (not part of `all`) times it against `eigen_symmetric` and `svd` for n = 3…16. At n = 9 it takes 11–12 µs, against 4–5 µs for `eigen_symmetric` and 14–23 µs for `svd`.
  - **Docs:** `docs/algorithms/eigenvalues.md` covers when to choose it, which was item 3 of #565.

- **`svd(A, s, V)`, a V-only SVD with QR preconditioning, and `null_vector(A)`** (#566). The full `svd(A, U, S, V)` always forms the m × m U, then runs one-sided Jacobi over all m rows. A null-space caller (8-point 2k × 9, DLT 2k × 12) needs only V's last column. It paid 500 µs at 64 × 9 and 0.24 s at 400 × 9, almost all of it completing U to a full basis.
  - **What it computes:** the new overload returns the singular values (descending) and the n × n V, and never forms U. `null_vector(A)` returns V's last column, the unit vector minimizing ‖Ax‖.
  - **How:** for a tall A it first reduces A = QR by Householder QR and runs Jacobi on the n × n R, which is Drmač and Veselić's preconditioner.
  - **Accuracy:** against the full `svd` on 10 × 3 to 400 × 12 matrices, including rows or columns scaled across 10⁸, the singular values agree to 1.3e-15 relative, and the columns of V to the same. For m ≤ n it runs Jacobi on A and matches the full `svd` bit for bit.
  - **Speed:** median times in µs, measured by the new `bench_all --suite null-vector` (not part of `all`).

    | m × N | `null_vector` | full `svd` | `eigen_symmetric`(AᵀA) | `eigen_symmetric_jacobi`(AᵀA) |
    |---|---|---|---|---|
    | 16 × 9 | 22 | 39 | 5.5 | 9.9 |
    | 400 × 9 | 34 | 238,543 | 15 | 18 |
    | 400 × 12 | 61 | 239,732 | 26 | 36 |

    It is slower than the AᵀA eigensolvers but does not square A's condition number. In `float` on 36 × 9 matrices whose second-smallest singular value is 1e-3, its null vector is off by 1.3e-5 rad, against 2.0e-2 for Jacobi on AᵀA. Most of its time is spent in the Jacobi sweeps on R: the shared one-sided Jacobi core divides every element by a scale factor on every pair, to stay safe from overflow. Making that cheaper would change the full `svd`'s bits, so it is left for a separate change.
  - **Backend:** both calls always use the generic C++ path, since LAPACK's `gesdd` has no V-only mode.
  - **Refactor:** the one-sided Jacobi loop moved into `detail::one_sided_jacobi`, shared by all `svd` overloads. The full `svd` returns bit-identical results to before.
  - **Tests:** `test_svd_null_vector` covers bit identity for m ≤ n (in `long double`, so a LAPACK build compares generic against generic), and agreement to rounding on graded tall cases. It also checks that `null_vector` recovers a known null vector of 2k × 9 and 2k × 12 systems for k = 8, 32 and 200, plus wide, square-singular and empty shapes.
  - **Not included:** a thin U (m × min(m,n)) is left for a follow-up.

### Changed

- **`eigen_symmetric`, `eigenvalue_symmetric` and `eigenvalue_symmetric_generic` default `tol` to machine epsilon and use LAPACK `dsteqr`'s deflation test** (#565). Results change: the in-house symmetric eigensolver returns different bits for most inputs. The LAPACK `syev`/`heev` path is unaffected, since it ignores `tol`. The default was `1e-10`, which capped accuracy far short of what the method reaches, the same problem `svd`'s default had (#337). A subdiagonal entry e between d₀ and d₁ was dropped once |e| ≤ tol·(|d₀| + |d₁|), a test that scales with the larger eigenvalue. It is now dropped once |e| ≤ tol·√|d₀|·√|d₁|, which scales with the smaller one. Measured on 9 × 9 and 12 × 12 normal matrices AᵀA with a known null vector (200 trials each): with the default `tol`, the smallest eigenvalue's eigenvector moves from 8.4e-12 to 9.0e-16 rad (N = 9) and from 9.1e-12 to 1.1e-15 (N = 12), and the new default accounts for all of it. With `tol = 1e-10` passed explicitly, the new deflation test alone lowers the error from 8.4e-12 to 2.0e-12. With `tol = ε` it changes nothing measurable. Neither change helps when A's columns are scaled across 10⁶: the eigenvector error stays at 6.6e-7 (N = 9) and 1.9e-6 (N = 12), because tridiagonal QR is only accurate to ε‖A‖ in each eigenvalue. Closing that gap is the job of the Jacobi solver in #564. mtl5-python's `eigh` and `eigvalsh` pass `tol = 1e-10` explicitly, so only the deflation change reaches them. `spectral_properties` uses the default. New tests in `test_eigen_symmetric` fail against the old header: a 2 × 2 case with `tol = 1e-6`, where the old test returned the small eigenvalue 2.5e-5 relatively wrong, and a null-vector case at the default `tol`. A third test checks that exactly zero eigenvalues still deflate under the stricter test. A custom real without a `std::numeric_limits` specialization reports `epsilon()` as zero, which would deflate only exact zeros: about a third of random 10 × 10 matrices then ran out of `max_iter` with eigenvalues ~5e-8 off, unreported. For such a type the default is measured instead (the spacing at 1, found by halving), and a non-positive `tol` maps to the default, as in `svd`. Found by CodeRabbit on #568.

### Documentation and maintenance

- **CMake declares a `3.22...4.2` policy range** (#571), in `CMakeLists.txt` and `ppe/CMakeLists.txt`. 3.22 stays the oldest supported CMake; a newer CMake now applies new-style behavior for every policy up to 4.2 instead of the 3.22 defaults. It is the same range as mp-blas, mp-iterative, mp-ode, mp-spice and Universal. Configuring with CMake 4.2.1 before and after registers the same 210 tests, with identical `CMAKE_CXX_FLAGS*` and no warnings.

## [5.15.0] - 2026-10-11

The QR counterpart of 5.14.0's Cholesky opt-in: an opt-in textbook Householder reflector, so a port pinned to a hand-written textbook QR or LQ can reproduce it bit for bit. Reviewing it turned up a `qr_solve` fix that applies to the default QR too. No breaking changes. The default reflector, `qr_factor` and `lq_factor` compute exactly what they did in 5.14.0.

### Added

- **`qr_factor(A, tau, tag::textbook_reflector{})` and `lq_factor(A, tau, tag::textbook_reflector{})`, and the same tag on `householder`, `apply_householder_left` and `apply_householder_right`: an opt-in textbook Householder reflector for bit-reproducible ports** (#559). The default reflector is LAPACK's form: x scaled by max|x|, v(0) = 1, τ = 2v₀²/(σ + v₀²), and R's diagonal non-negative. Many hand-written QRs use the textbook (Golub & Van Loan) form instead: unscaled ‖x‖, α = −sign(x₀)·‖x‖, unnormalized v with v(0) = x₀ − α, and a per-column update `f = (2·s)/vᵀv; A(i,j) -= f·v(i)`. The two round differently and, when x₀ > 0, reflect onto opposite signs. branes-ai/cortex's filter port saw 10 of 117 stage outputs move, its null-space projection change at O(1), and 1 of 16,265 update decisions flip on EuRoC V2_03. `householder(x, tag)` returns `{v, vtv, alpha}`. `apply_householder_left(A, v, vtv, row, col, tag)` applies it, threaded over columns, and `apply_householder_right(A, v, vtv, row, col, tag)` applies it on the right, threaded over rows, so neither result depends on the thread count. Zero and NaN columns are skipped with a hand-written loop's own tests, `!(norm > 0)` and `!(vᵀv > 0)`. The tagged `qr_factor` never dispatches to LAPACK. Its R, on and above the diagonal, is bit-identical to a textbook QR, signs included. Below the diagonal and in `tau` it stores the same reflector in MTL5's packed form (v/v(0), τ = 2v(0)²/vᵀv), so `qr_extract_Q` and `qr_solve` work unchanged, with Q matching the textbook Q to rounding. The tagged `lq_factor` is its row mirror: L, on and below the diagonal, is bit-identical to a textbook LQ, and `lq_extract_Q` works unchanged. The default overloads are unchanged. Real element types only. The tag lives in `<mtl/tag/reflector_form.hpp>`. `test_householder_textbook` checks each tagged path against reference textbook loops with `==` on `double`, `float` and a class-typed scalar, including skipped zero and NaN columns and 300 × 2000 and 2000 × 300 updates split across 4 threads; it is built with `-ffp-contract=off`. `docs/numerical/householder-reflector-forms.md` covers the why, what and how.

### Fixed

- **`qr_solve` skips a reflector with τ = 0** (#559). τ = 0 is the identity reflection, and the column below the diagonal then holds the column's own entries, not a reflector. `qr_solve` applied it anyway as `y -= 0·v·(vᵀy)`, which is NaN as soon as one of those entries is NaN, so a skipped NaN column turned the whole solution into NaN. Both the default and the textbook `qr_factor` leave τ = 0 for such a column. `qr_extract_Q` already skipped it, since `apply_householder_left` returns early on a zero τ. Finite inputs are unaffected, except that a zero in y can no longer change sign through `y − 0`. Found by CodeRabbit on #560.

### Documentation and maintenance

It covers `MTL5_BUILD_REGRESSION_TESTS`, how to run the tier with the `ci-regression` preset and the `regression` CTest label, and what each of the 14 programs in `tests/regression/` checks, with problem sizes and pass thresholds. It also gives the per-test time limits, and when CI runs the tier: non-draft PRs only, after the 8-platform `build` job.

## [5.14.0] - 2026-10-11

Three changes driven by branes-ai/cortex's port of a Kalman filter onto MTL5: two speed up `mult()` on the small, structured operands of filter covariance algebra, and one lets a port pinned to a hand-written Cholesky factorization reproduce it bit for bit. No breaking changes. `cholesky_factor`'s default results are unchanged except that a NaN pivot is now reported as an error instead of returning success.

### Performance

- **The generic dense GEMM runs as an i-k-j loop when B and C are row-major** (#549). `detail::mult_generic_rows` was an i-j-k dot product. Its inner loop walks B down a column, and its single accumulator is a sequential reduction the compiler cannot vectorize, so it ran 1.5–2.6× slower than an i-k-j loop. Those numbers are from 15–81-wide shapes in branes-ai/cortex's filter covariance algebra. The kernel now keeps C's row as the accumulator and adds `A(r,k) * B.row(k)` for each k. That inner loop is contiguous and independent, so it vectorizes. Each `C(r,c)` is still built as zero plus the products in ascending k with the same `generic_fma`, so **results are bit-identical** for every scalar type when the compiler does not contract `acc + a*b` into an FMA. That holds under `-ffp-contract=off`, and on targets without FMA such as baseline x86-64. Under contraction, the i-k-j loop fuses every term while the old loop fused only some, so the two agree to rounding but not to the bit. `test_mult_ikj` compares bits against the old loop, including -0 and infinities, and is built with `-ffp-contract=off` like the other bit-identity tests. Other layouts and the custom-`Accumulator` path keep the dot-product loop. Measured at `-O3`, gcc 15, no `-march`: P·P (81×81) 142 → 75 µs; P·Hᵀ (81×81·81×15) 30 → 18 µs; K·H (81×15·15×81) 25 → 14 µs.

### Added

- **`cholesky_factor(A, tag::subtract_term_by_term{})`: an opt-in summation order for bit-reproducible ports** (#556). `cholesky_factor` forms each entry as `a − (Σ products)`: it sums the products from zero, then subtracts once. Many hand-written factorizations instead start from the matrix entry and subtract term by term. Both forms are backward stable, but they round differently, so a port pinned to the term-by-term form couldn't move to MTL5 without changing bits. branes-ai/cortex's filter port saw 37 of 117 stage outputs move and 2 of 16,265 update decisions flip on EuRoC V2_03. The new overload selects the term-by-term form. It never dispatches to LAPACK, whose order is its own, and it keeps the same row-partitioned threading, so the result doesn't depend on the thread count. `cholesky_factor(A)` is unchanged, and `tag::subtract_sum` names the default explicitly. The tags live in `<mtl/tag/summation_order.hpp>`. `test_cholesky_ordering` checks the opt-in against a reference term-by-term loop with `==`, on `double`, `float` and a class-typed scalar up to n = 768 with 4 threads. It is built with `-ffp-contract=off`, like the other bit-identity tests. Neither order is more accurate across the board: term by term is ahead on ill-conditioned spectra and sum-then-subtract on well-conditioned ones, both within a small multiple of the unit roundoff. The new **Numerical Considerations** docs section, `docs/numerical/summation-order-in-cholesky.md`, covers the why, what and how with measurements and a worked example.

- **`mult(compressed2D A, dense2D B, dense2D C)`: a sparse × dense matrix product** (#550). It previously fell to the generic kernel, which reads `A(r,k)` by binary search for every (r, c, k). It now walks A's stored entries row by row (`detail::mult_sparse_crs_dense_par`, threaded over row bands like the sparse matvec): `C.row(r) = Σ v · B.row(k)` over A's entries in ascending k. That is the dense product's summation order with A's zero terms left out, so it equals the dense result bit for bit whenever those terms are exact zeros (with the same contraction caveat). With BLAS enabled, `mult()`'s BLAS gate no longer instantiates `is_row_major_v` for operands without an `orientation`. Before, that was a compile error for a `compressed2D` or `transposed_view` operand. The test checks this, and checks agreement with the column-by-column sparse matvec. B and C must be row-major dense; other layouts are unchanged.

### Fixed

- **`cholesky_factor` rejects a NaN pivot** (#556). The generic path tested `diag <= 0`, which is false for NaN, so a NaN in A returned 0 (success) with NaNs in L. It now tests `!(diag > 0)`, as `cholesky_h_factor` already did, and returns k+1 for a NaN pivot in either summation order. Finite inputs are unaffected. The LAPACK path's behaviour is `potrf`'s own.

### Documentation and maintenance

It shows the filter operands' non-zero structure (F = Φ ⊕ I is 4.4 % non-zero; the Joseph factor I − KH ranges from 27 % to 100 %), explains why the i-k-j order vectorizes while keeping each element's summation order, and gives an interleaved before/after on an i7-12700K with hand-written control loops in both builds. Results: P·P (81×81) 137 → 76 µs at baseline x86-64 and 141 → 53 µs with AVX2; F·P 635 → 3.6 µs. The A/B source is `benchmarks/bench_mult_ikj.cpp` and the figures come from `benchmarks/fig_mult_ikj.cpp`. Both are registered under `MTL5_BUILD_BENCHMARKS`.

## [5.13.2] - 2026-10-11

A patch release: the scalar operators work with the custom number types MTL5 is built for, and the eigensolvers' accumulator tests can now tell the two policies apart.

### Fixed

- **`scalar * matrix`, `matrix * scalar`, `matrix / scalar` and their vector forms accept any non-container `Scalar`** (#548, resolves #538). The six operators were gated on `std::is_arithmetic_v<S>`, which rejected posits, `cfloat`, LNS, fixed-point and `std::complex`, even though all of them satisfy `mtl::Scalar` and `mtl::Field`. It turned up in a Kalman filter over posits: `K = P H^T / S` did not compile. The gate is now `!Collection<S> && Scalar<S>`. The `!Collection` check comes first and short-circuits, because evaluating `Scalar<S>` for a matrix or vector operand would recurse into these same operators. `matrix * matrix`, `matrix * vector` and built-in scalars resolve as before, and a new test checks that.
- **The eigensolver accumulator tests can tell the policies apart** (#547). This resolves the follow-up recorded in the 2026-10-10 session log below. In the earlier `power_iteration`, `lanczos` and `arnoldi` tests, a `float` accumulator and a `double` one both reached the 1e-4 tolerance floor, so a solver that ignored the accumulator would still pass. Each solver now has a test on a 1024×1024 diagonal (`2^20`, 1022 × `2^-5`, `-2^20`) whose Rayleigh quotient cancels. A `float` accumulator gets exactly 0, a `double` accumulator gets the exact value, and the test fails if the accumulator is ignored. Arnoldi's second Gram–Schmidt pass leaves its result 0.2% high, so it is checked to within 1%. The original tests are kept, renamed to say what they check: that both policies converge.

### Documentation and maintenance

- **Session log for 2026-10-09 – 2026-10-10**: `docs/sessions/2026-10-10-every-test-overrode-the-default.md`. Covers the leading-`Accumulator` convention (#539, #540, #542), the 5.13.0 and 5.13.1 releases, and the downstream bumps in mp-iterative, mp-spice and mtl5-python. Its through-line is the 5.13.0 regression: every test accumulator overrode `clear()`, the one function that was broken, so the suite never ran the default it fell back to. It also records an open follow-up: the restored Lanczos accumulator test (#540), and the Arnoldi test it was rewritten from, can't tell a `float` accumulator from a `double` one, since both only need to reach a 1e-4 floor. ## [5.13.1] - 2026-10-10

A patch for one regression in 5.13.0. **If you use Universal's `lns` types, or any arithmetic type whose value-initialized state is not zero, upgrade.**

### Fixed

- **`accumulator_traits::clear()` sets zero, not a value-initialized `Acc`** (#544). `clear()` reset with `a = Acc{}`, assuming value-initialization is zero. That holds for every built-in type but not in general. A logarithmic number system encodes 2⁰ in its all-zero bit pattern, so Universal's **`lns{}` is 1.0**, and every sum of products over an `lns` accumulator started at 1. 5.13.0 made this reachable without opting in: #537 routed `householder()`'s sum of squares through `clear()` on the **default** path, where 5.12.0 had started it at `mag_t(0)`. As a result **QR and LQ over `lns` were wrong outright** (Q orthogonality error 1.5, QR residual 0.53 for lns16 and lns32), and with them everything built on Householder reflectors. mtl5-python's suite caught it on the v5.13.0 bump. `clear()` now assigns `math::zero<Acc>()`. `fma_accumulator` had the same flaw in its `clear()` and in its member default `T sum{}`, and both are fixed. An audit found every other accumulator declaration and workspace is cleared or assigned before it is read. The suite had missed this because every test accumulator specialized `accumulator_traits`, so none exercised the primary template. The new regression test uses a mock type whose value-initialization is 1.

## [5.13.0] - 2026-10-10

One programme: **the accumulator policy reaches the rest of BLAS and the solvers** (#261 Part C). `accumulator_traits<Acc, Value>` lets a caller choose how a sum of products is rounded: wider IEEE, FMA, or a quire through the peer repos. Until this release that choice was available on `dot`, `mult`, `norms`, the Krylov solvers and four sparse factorizations. It now covers every BLAS L1/L2/L3 routine, the sparse Cholesky/LDLᵀ/QR factorizations, Householder reflectors, and the three iterative eigensolvers. The release then settles **one calling convention for all of them**: `Accumulator` is the first template parameter, so `op<Acc>(args...)` selects it and everything else is deduced.

Breaking changes, all in explicit template arguments; calls that deduce everything are unaffected. **Read the first entry before upgrading** — it is the one place an old call still compiles but means something different.

### Breaking

- **`axpy`, `scale`, `ger`, `symv`, `trmm`, `trsm`, `symm`, `syrk`, `syr2k`: the first explicit template argument is now the accumulator, not the scalar type** (#511, #515, #522–#526). Each gained a leading `Accumulator = void` in front of `Scalar S`. A 5.12 call that fixed the scalar type explicitly, e.g. `axpy<float>(0.1, x, y)` meaning "convert alpha to `float`", **still compiles** and now means "accumulate in `float`, alpha stays `double`". Results can differ with no diagnostic. To keep the old meaning, convert the argument instead: `axpy(float(0.1), x, y)`. Explicit lists on `trmv`, `trsv`, `lower_trisolve` and `upper_trisolve`, whose first parameter was the matrix type, fail to compile rather than change meaning.
- **Krylov solvers take a leading `Accumulator`** (#539). `cg`, `bicg`, `bicgstab`, `bicgstab_ell`, `cgs`, `gmres`, `minres`, `qmr`, `tfqmr` and `idr_s` had it *last*, after five deduced types, so it could only be set by restating all of them: `itl::cg<M, VX, VB, PC, Iter, Acc>(...)` is now `itl::cg<Acc>(...)`. Old full lists fail to compile. Downstream: mp-iterative updated in its #44.
- **Sparse numeric factorizations take a leading `Accumulator`, defaulting to `void`** (#542). `sparse_lu_numeric`, `native_klu_factor`, `supernodal_lu_numeric` and `supernodal_ldlt_numeric` had `Accumulator = Value` last, so a caller had to spell out the matrix's internal parameter type: `supernodal_lu_numeric<double, decltype(A)::param_type, float>(A, sym)` is now `supernodal_lu_numeric<float>(A, sym)`. A leading default cannot name `Value`, so the default is `void`, resolved to `Value` inside; default calls are byte-identical. Old full lists fail to compile. A single explicit `<Value>` still compiles and behaves as before. Downstream: mp-spice updated in its #18; **mtl5-python's five call sites in `mtl5_sparse_direct.cpp` need the same change when its pin moves past v5.11.0**.
- **`power_iteration`, `lanczos`, `arnoldi`: explicit `<LinearOp, T>` no longer compiles** (#540). These gained an accumulator in this release (#518, #528, #529), placed leading with a `void` default that means "accumulate in `T`". A 5.12 call that named the operator and value types explicitly now fails to compile; drop the arguments, both are deducible.
- **`sparse_cholesky_numeric`, `sparse_ldlt_numeric`, `sparse_qr_numeric`: explicit `<Value, Parameters>` no longer compiles** (#530, #531, #534, #542). The same shape as the entry above for the sparse factorizations that gained an accumulator in this release. A single explicit `<Value>` still works.

### Added

- **Accumulator policy for the BLAS L1 remainder: `axpy` and `scale`** (#511). `axpy` is a one-term sum of products seeded with `y(i)` rather than zero, so it is the **first caller of the contract's `assign`**. A test asserts the operation counts directly (axpy drives `assign` and never `clear`; scale the reverse), which turns #261 Part A's "audit the call sites" from a reading into a check. `scale` sums nothing; what a non-default accumulator buys it is widening, and the entry says so. The accumulator sees the scalar at its own precision: a wider alpha is no longer rounded to the element type before `add_product`.
- **Accumulator policy for BLAS L2: `ger`, `symv`, `trmv`, `trsv`** (#515, #516). `gemv` was already covered through `mult`. `trsv` delegates its reduction to `lower_trisolve`/`upper_trisolve`, so both trisolve headers carry the accumulator too. `trsv`'s BLAS dispatch is now gated on `accumulator_allows_blas_v`, which it previously was not.
- **Accumulator policy for BLAS L3: `trmm`, `trsm`, `symm`, `syrk`, `syr2k`** (#522–#526, sub-issue #521). In each, the reduction is accumulated and rounded out once; `alpha`/`beta` and the triangular division are applied afterwards, outside the accumulator. The upper-triangle mirror in `syrk`/`syr2k` is a plain copy, not a re-sum.
- **Accumulator policy for `sparse_cholesky`, `sparse_ldlt` and `sparse_qr`** (#530, #531, #534). This completes the sparse direct line alongside `sparse_lu`, `native_klu`, `supernodal_lu` and `supernodal_ldlt`. In `sparse_ldlt` the per-term square is still rounded in `Value` before reaching the accumulator, a limit documented at the call site.
- **Accumulator policy for Householder reflector construction and application** (#537). `householder`'s sum of squares and the per-column/per-row dot products in `apply_householder_left/right`. The default path keeps the threaded fast path untouched; a non-default accumulator runs a serial loop, since the threaded combiner does not reason about a caller's accumulator type. **Not yet reachable from `qr`/`lq`/`svd`**: `qr` calls `apply_householder_left` without forwarding an accumulator. Tracked in #261.
- **Accumulator policy for the iterative eigensolvers: `power_iteration`, `lanczos`, `arnoldi`** (#518, #528, #529, sub-issue #527). These route the Rayleigh quotient, Lanczos's α/β and Arnoldi's Hessenberg entries and residual norm through the accumulator. On the well-conditioned test problems the error is dominated by Krylov convergence, not accumulation, so the accuracy tests assert both configurations reach the tolerance floor rather than a strict ordering.
- **The eigensolvers' `tol` is non-deduced** (#540). It is now `std::type_identity_t<T>`, so `power_iteration(A, v_float, 1000, 1e-6)` compiles. `T` comes from the vector alone; before, a `double` literal tolerance conflicted with a `float` vector in deduction.

### Fixed

- **SIMD scalar tails round the way the vector body does** (#513, resolves #512). `reduce_dot`, `reduce_dot_widen`, `reduce_sum_squares` and `axpy` used `fma()` in the vector body and a plain multiply-add in the scalar tail, so an element's rounding depended on its index. For `axpy`, where every element is an independent output, the first `W·⌊n/W⌋` entries were computed differently from the rest. The tail now applies the body's own batch primitive to a broadcast and reads one lane back. Mirroring Highway's `MulAdd` branch instead failed on clang + Highway, and a decomposed `c + a*b` could be re-contracted under `-ffp-contract=fast`.
- **The Lanczos accumulator test is back** (#540). #529 rewrote it in place into the Arnoldi test instead of adding one alongside it, which left `lanczos`'s accumulator path untested; the suite's case count did not move because the whole file is one ctest entry.
- **`test_integer_wrapping_generic` builds on glibc 2.43** (#541). glibc now declares C2y's `uabs` in `<stdlib.h>`, which made the test's own `uabs` ambiguous on GCC and Clang. It is renamed `abs_as_u32` and the reference helpers moved into `mtl::test`.

- **The release checklist starts from the commit range, not from memory** (#510), after the 5.12.0 CHANGELOG covered 7 of 28 PRs. The 5.12.0 entry was completed in #509.

## [5.12.0] - 2026-08-27

Two programmes. **On-node parallelism for emulated formats** — the threaded
kernels that the BLAS-scalar gate had been keeping them out of — together with the
completion of #450's integer exclusion through `itl/`. And **the nc model**: the
jc partition made measurable, timed on four microarchitectures, and then adopted
as the default on evidence rather than argument.

Two breaking changes, both narrow and both removing instantiations that already
returned wrong answers; see **Breaking** below before upgrading.

### Breaking

- **`mtl::itl` requires a `Field` element type — solvers, preconditioners and smoothers** (#503, #505). Every Krylov solver computes its step lengths as ratios in the element type: `cg`'s `beta = rho / rho_1` and `alpha = rho / dot(p, q)`, ten such divisions in `qmr`, eight in `tfqmr`, at least two in every one of the ten including `cgs` and `gmres`. On an integral type that division **truncates**, so the iteration was nonsense from the first step — it ran, it converged or it did not, and it returned a confident wrong answer with no assertion and no flag. The preconditioners and smoothers are a **separate entry point**, constructed before any solver sees them, so `pc::ilu_0<int> M(A)` truncated its factorization at construction and a solver gate would never have fired. This is #450's `lu_factor(dense2D<int>)` one and two levels up: ℤ is a ring, not a field. New `FieldVector` (the vector counterpart of `FieldMatrix`) gates the eleven solver entry points including `gmres_inner`; `FieldMatrix` and `Field<Value>` gate the eighteen preconditioner and smoother types. **What breaks downstream:** integral element types in `itl` no longer compile. Every affected call site was already wrong — for `diagonal`, `jacobi`, `gauss_seidel` and `sor` it was worse than truncation, since `value_type(1) / A(i, i)` is **0 whenever |A(i,i)| > 1**, making the preconditioner the *zero operator*. float, double, complex and the custom number types are unaffected
- **`ilut`'s threshold parameter is the real magnitude type, not the element type** (#505). `magnitude_t<Value>`, which **is** `Value` for every real element type, so real users see no change. It was `Value`, which made `abs(w[k]) < drop_tol` compare a `double` against a `complex<double>`: `ilut<complex<double>>` named a valid type whose `factorize()` did not compile

### Added

- **Threaded dense GEMV and GEMM for non-BLAS scalar types** (#446). `is_blas_scalar_v` gated two unrelated questions at once — *"may this go to OpenBLAS or a SIMD micro-kernel?"* and *"may these output rows be split across cores?"*. Only the first is about the scalar type; a row partition hands each worker a disjoint set of output elements and runs the same per-element code the serial loop would. Every software-emulated format — posit, cfloat, lns, the dd/qd cascades — therefore ran its dense matvec and matmul on **one core** regardless of `MTL5_NUM_THREADS`. New `ThreadableDenseMatrix` / `ThreadableDenseVector` carry the storage shape only, with no constraint on the element type, and gate a row-partitioned wrapper around the **generic** kernel — deliberately not a reroute into `gemm_blocked`, which earns its keep through a vectorized micro-kernel and measured ~3.4× *slower* for a type Highway cannot vectorize. Measured on an i7, GEMM n=384 on a class-typed scalar, min of 5: flat before (**0.120 / 0.177 / 0.113 / 0.117s** at 1, 2, 4 and 8 threads) against **0.115 / 0.062 / 0.031 / 0.049s** after — **3.7× at four threads**. Bit-identical at every thread count, asserted with `==` rather than a tolerance
- **Threaded sparse CRS matvec in `mult`** (#446 follow-up). `mat::operator*(compressed2D, dense_vector)` had threaded this traversal for any value type since #221, but `detail::mult_sparse_crs` — the accumulator-aware kernel `mult(compressed2D, x, y)` dispatches to, and the one a mixed-precision sweep calls — ran it serially. The gather from `x` is what makes the forward kernel safe to partition and its transpose not. **3.8× at four threads, 4.8× at eight** on a scalar whose multiply costs what an emulated format costs. The honest counterweight is recorded with it: on a *cheap* scalar the same kernel gains only **1.18×**, because a `double` SpMV is memory-bandwidth-bound and the cores have nothing to do
- **`parallel_chunk_units<T>` and `row_grain<T>`** (#446). The 65536-unit chunk budget is a wall-clock quantity counted in operations, so it only fits a type whose multiply-add is one instruction. Charging an emulated format the same costs **parallelism**, not overhead: `parallel_for` caps the team at `n / grain` chunks, so a posit GEMM at n=64 would form four and idle half an eight-way pool. Class types get 1024. Unchanged for float/double — `row_grain<double>(nn)` **is** `65536 / nn`

#### The nc model: making the jc partition measurable, then choosing one (#479, #492)

- **The prerequisites that need no hardware** (#480). `balanced_nc` (the jc counterpart of `balanced_mc`), the two mediators `grid_imbalance` and `packed_b_bytes` recorded per point by `bench_blocking_ab`, models M0–M5 as pure functions, and `sweep_nc_models` to enumerate offline *where they disagree*. `balanced_nc` is deliberately **not** wired into the nest here — measuring whether it should be is a separate step from applying it. The work caught a defect in itself: `balanced_nc` first rounded the balanced `nc` up to a multiple of `nr`, which **undid the balancing** — a pre-registered control caught `m4_per_sharer` at n=276681 going from a perfectly even partition to 1.0038, the balancing step making the imbalance *worse*
- **The harness arm that made the models timeable** (#484). `gemm_blocked` read its jc block size from a compile-time constant, so six candidate models could be enumerated but not timed. Gated, every control keeps M0's `nc` **by construction** and cannot move

### Fixed

- **Integer overflow is no longer UB in the sparse and remaining L1 generic loops** (#461). #460 defined the wrapping contract for the dense path; these loops were outside it and still accumulated with a plain `+=` / `*=`. Routed through `detail::generic_fma` and two new siblings — `generic_add` for the loops that accumulate a term they did not form by multiplying, `generic_mul` for `scale` — across `mult_sparse_crs` and its transpose, `axpy`, `scale`, six accumulations in `norms`, and the eager `operator*` loops in `mat/operators.hpp`, which were not on the issue's list but are the same defect two lines from one that was. All are the plain expression for every non-integral type, so float, double, posit, LNS and fixpnt are unaffected
- **`std::abs` at the minimum of a signed type** (#461). UB — there is no positive 2^(N−1) — so `one_norm(dense_vector<int32_t>)` over full-range data was undefined *before any accumulation happened*, and it is reached by exactly the test the wrapping fix requires. New `generic_abs` returns the wrapping answer. The consequence is recorded rather than hidden: the wrapped |min| is negative, so it never wins `infinity_norm`'s max — an integer norm is **defined** and reduced mod 2^N, but it is only a *norm* when nothing overflowed
- **`ilut` could not be instantiated with a complex element type** (#505). Two causes: the threshold typing above, and two `std::sort(entries.begin(), entries.end())` calls that compared pairs lexicographically, requiring an ordered element type for a `.second` comparison that unique column indices meant never happened at runtime. Both fixed; the row 2-norm now accumulates |a|² rather than a², which agrees for real elements and is only a norm for complex ones
- **The ThreadSanitizer CI lane discovers its own targets** (#446). It built a hand-maintained list of `*_mt` targets but ran `ctest -R _mt`, which finds every `_mt` test whether or not it was built — so adding one failed the lane with `Could not find executable`, reported as a test failure inside a TSan job, which reads as a race and is not one
- **`balanced_mc` could return a block shorter than the register tile** (#488, fixed in #489). `plan_gemm_grid` floors `mc` at `mr` and says why in its own comment — "a block shorter than `mr` would waste the micro-kernel" — and `balanced_mc` then ran and lowered it straight back through that floor, because balancing works by *raising* the block count. At `mc=5` against `mr=6`, **every** ic block takes the micro-kernel's edge path, not just the trailing one it was written for. The argument for the change is not "sub-tile is wasteful": exhaustively over the 383,934 parameter combinations where the answer moves, the **padded** rows on the busiest thread are *identical* before and after — the old rule looked better balanced only in raw rows, and the padding erased exactly that difference. What did change is the total: the new answer does less work across all threads in **94.9%** of those cases, 2.28× less on average, 16× at best, and more in none
- **`packed_b_bytes` reported a panel larger than the nest builds, three ways** (#486, fixed in #496). It is the mediator #479 records per point and the left-hand side of M6's guard, so it has to be *true* rather than approximately true. It used the **accumulator** type where the panel is a `packed_buffer<TB>` (2× off for float operands into an fp64 accumulator, 4× for i8 into i32); it ignored the **column padding**, since `balanced_nc` deliberately does not round `nc` to a multiple of `nr` on the threaded path — so a ragged `nc` is the normal case, and this one was wrong even for `double`; and it ignored the **quad k-padding**. Resolved by answering #486's three questions rather than by making `nc` bigger, which a naive reading would have done and which the data says is the wrong direction
- **The benchmark harness measured warmup and called it convergence** (#493, fixed in #494). `bench_nc_models` printed "worst first-round excess over the minimum … (raise `--rounds`)" computed from round 0, which is a **warmup** question — raising `--rounds` cannot change round 0 at all. It misled in practice: on the Xeon session behind #485 it fired at 45.62% and advised doubling the machine time for a session whose 24 control arms agreed to within **1.48%**, and the false judgement was written into a committed sidecar. Now two numbers for two questions — convergence as the best time over all rounds against the best over the earlier two thirds, and warmup as a diagnostic only
- **The machine-identity guard never worked on ARM** (#487). `grep -m1 'model name' /proc/cpuinfo || tr -d '\0' < /proc/device-tree/model` — and `A || B` runs B only when A *fails*. On ARM the grep **succeeds**, returning a generic `ARMv8 Processor rev 1 (v8l)` with no board identity, so the device-tree fallback never ran on the one architecture that needs it. #439's protection — do not write one machine's numbers into another machine's directory — was silently off on the Jetson for every sweep already committed. It failed in the *safe* direction, refusing a machine that was an Orin, which is why it was noticed; had the expected substring been something the generic ARM string contained, it would have accepted anything

The integer-lane release. `batch<T>` gains 32-bit integer lanes, the two widening
dot kernels the hardware has instructions for, an integer GEMM, and the VNNI /
SDOT micro-kernel that puts those instructions inside a GEMM — measured on four
machines across two ISAs. **No breaking changes.**

**Two fixes here change results for existing `float`/`double` code** and are worth
reading before upgrading: a **GCC 13 miscompile** of AVX2 integer reductions, and
**strided vector views reaching contiguous fast paths** through ten operations —

### Added

#### Integer lanes, and the widening dot kernels the epic was for (#451)
- **`batch<T>` accepts `int32_t` and `uint32_t` lanes**, so `dot` and both `gemv` orientations run the SIMD kernels for integer vectors instead of falling to the generic scalar loop (#460). The boundary is deliberate at both ends: 8- and 16-bit lanes are worth having only *with* the widening accumulate they exist for, and 64-bit integer multiply is emulated before AVX512DQ, so a `batch<int64_t>` would advertise a vector multiply that is a scalar loop in disguise. Integer arithmetic is **two's-complement wrapping** — what Highway specifies and what every target ISA does — which buys a property floating point cannot offer: addition mod 2³² is associative, so an integer reduction is **bit-identical across lane counts, unroll factors, backends and thread partitions**. The tests assert exact equality against a closed-form reference and never mention accumulation order. Division is not offered on integer lanes, matching the position #450 took one level up
- **`dot<int32_t>` over `int16_t` uses the hardware widening multiply-accumulate** (#463) — `vpmaddwd` on x86 (`pmaddwd` at SSE), `SMLAL`/`UMLAL` on NEON — one instruction for the widen, the multiply and the accumulate, verified at the instruction level rather than only by value. 16-bit types are **operands, not lanes**: `batch<int16_t>` deliberately does not exist, because a 16-bit lane's value *is* this accumulate. The overflow contract is the substance: products are always exact (|−2¹⁵·−2¹⁵| = 2³⁰ fits an int32), but the **sum wraps soon** — worst case at k = 3, ~36 for random signed data. The useful regime is small operands rather than short vectors: at *b* bits of operand magnitude the headroom is ~2^(31−2b) terms. This kernel may use an instruction the float one may not, because `ReorderWidenMulAccumulate` permutes which product lands in which lane and guarantees only the total — disqualifying for a floating accumulator, unobservable on integer lanes
- **`dot<int32_t>` over 8-bit operands uses the quad multiply-accumulate** (#464) — `vpdpbusd` on x86, `SDOT`/`UDOT` on NEON — four products into each 32-bit lane per instruction. Verified as **codegen** on icelake-server, sapphirerapids and znver4, which matters because Cascade Lake has AVX512-VNNI without Highway's full `HWY_AVX3_DL` set and so takes the decomposed path with identical results and more instructions. Eight bits is the width that matters for **headroom**, not lanes: halving the operand quarters the product, so the same int32 accumulator holds ~131 000 terms for `i8×i8` against 3 for `i16×i16` — four to five orders of magnitude, and the reason the quantized-inference instructions are 8-bit. Tested rather than asserted: 100 000 worst-case int8 terms sum exactly. The signedness asymmetry is handled at **two levels**: `simd::reduce_dot_widen` offers exactly the three pairings the instruction offers and rejects `(int8, uint8)` at compile time naming the fix, while `dot`/`dot_real` accept every pairing and stay fast by swapping the operands onto the native instruction — a dot product is symmetric, so refusing one for a hardware reason would break generic code and dropping to the generic loop would cost an order of magnitude unremarked
- **Integer GEMM: same-type int32, and 8/16-bit operands accumulated in int32** through the blocked nest's widening load (#468). The nest, the packing and the micro-kernel needed **no changes** — they were already generic over (accumulator, operand) from #176; what was missing was `batch::load_widen` for integers, which phase 0 had disabled pending the signedness convention and overflow contract that #463/#464 then supplied. The tests include one a float GEMM cannot make: the blocked nest must be **bit-identical** to the naive triple loop, because it reorders the k loop across `pc` blocks, partitions m across threads and accumulates in a register tile — all of which is addition mod 2³², which is associative

#### Benchmark integer arms, and the guard that is their substance (#465)
- **`--suite int`** runs fp64/fp32 baselines against int32, int16→int32, int8→int32 and uint8×int8→int32 for `dot`, and int32 for `gemv`, at identical sizes so the comparison lands in one CSV. The dot sweep is by **footprint** — 1K to 4M elements, L1 through DRAM — because a dot is a streaming reduction and two effects must be separated: at large *n* it is bandwidth-bound and int8 moves one byte per element against fp64's eight, so a ~8× speedup is expected on **any** machine, VNNI or not, while the instruction only shows at L1-resident sizes
- **`run_int_bench.sh` refuses to time a build without the instruction it claims to measure.** Nothing in a timing distinguishes `vpdpbusd` from the `vpmaddwd` decomposition, and having the hardware is not sufficient — Highway selects its VNNI target only on the full AVX3_DL conjunction (VNNI plus VBMI, VBMI2, BITALG, VPOPCNTDQ, VAES, VPCLMULQDQ), so an AVX-512 machine with VNNI can still compile to the slow path, and **MSVC defines none of those macros**, so the existing MSVC Zen 4 profile cannot produce a VNNI build. `--allow-decomposed` measures it anyway and labels the run so the CSV cannot be mistaken. Both guards were tested by firing them. `build_isa` now carries `AVX512VNNI`, `AVX3_DL`, `AVX10.2`, `DOTPROD` and `I8MM`, since it previously recorded `AVX512F` and stopped

#### The VNNI / SDOT GEMM micro-kernel (#469)
- **`mult_quad` drives the hardware quad multiply-accumulate** — `vpdpbusd` on x86, `SDOT`/`UDOT` on NEON — four k-values per instruction against the widening path's one. `vpdpbusd` consumes four k-values at once, so it needs a **quad-interleaved pack** (`Ap[…][i*4+q] == A(i, 4g+q)`, and the same for B, with k zero-padded to a multiple of four) and a micro-kernel whose left operand is a **broadcast quad** rather than a broadcast scalar: a 32-bit splat of four bytes, so lane *j* accumulates `sum_{q<4} A(i,p+q) · B(p+q,j)`. `gemm_blocked` gains `TA`/`TB` as separate operand types — `(u8,i8)` is VNNI's native shape and the two must differ — plus a `gemm_kernel` template argument; the five loops, cache blocks, thread grid, cooperative B-pack and exception handling are shared, since none of them depend on which micro-kernel runs. `(i8, u8)` is **rejected rather than reordered**: a dot product is symmetric so swapping fixes it there, but a GEMM is not, so column-major C — computed as `C^T = B^T A^T` — cannot take the asymmetric pairing and falls to the generic loop
- **The kernel selection is an explicit template argument, not inferred from the element types.** It was inferred at first, and since `(i8,i8)` is valid input to *both* kernels that silently rerouted `mult`'s widening path — through a **completely green test suite**, because the two kernels agree **bit for bit** and no result can tell them apart. The benchmark caught it: the two int8 arms began reporting the same number to three digits, so the arm meant to be the control had stopped being one. `gemm_kernel::widening` is the default, `mult` is unchanged, and a **structural** test pins the default since a result-based one provably cannot
- **`has_native_quad_dot_v<NA, NB>` reports quad support per operand pairing**, because the hardware is per pairing and the two ISAs implement **opposite** ones first: x86 gets `u8×i8` at AVX3_DL and the symmetric pairings only at AVX10.2; ARM gets `i8×i8`/`u8×u8` with FEAT_DotProd and `u8×i8` only with I8MM. A single flag mislabelled at least one arm on every machine measured, and a cross-machine comparison that pairs arms by *name* gets the sign of the effect wrong — the fastest arm inverts between Zen 4 and a Cortex-A78. `quad_dot_native_support` summarises as `none`/`partial`/`all`, and **`partial` is what every machine measured so far reports**. `has_native_quad_dot` keeps its original *any-pairing* meaning so no committed sidecar changes meaning. The gates now use Highway's own conditions (`HWY_TARGET <= HWY_AVX3_DL` is literally the gate in `x86_128-inl.h`) rather than a hand-reconstructed seven-macro AVX-512 conjunction
- **Committed int-suite run profiles for all four machines** (`benchmarks/machines/*-int.sh`), so the arch flag, pin list, output directory and `--allow-decomposed` decision live in the repository. The two decomposed profiles assert `--allow-decomposed` on the operator's behalf — on those parts the decomposition *is* the measurement — while the two native ones deliberately do not, so a build that misses its ISA stops. The Xeon pins `0,1,2,3,4,5` where every other profile pins `0,2,4,…`: its SMT siblings are blocked `(0,6)`, not adjacent pairs
- **`verify_gemm_int` checks every integer GEMM arm against a 64-bit reference**, outside the timed region, and **fails the run** rather than warning. `measure` only invokes the lambda and records elapsed time, so before this no GEMM arm ever *read* its output: a kernel returning nonsense produced a well-formed CSV row, and an unread output is also the shape of work a compiler may delete

### Changed

- **The integer-lane results are recorded in the living assessment, and the i7 corrected them** (#467). On a Zen 4 with native `vpdpbusd`, `dot` with `uint8 × int8` reaches **26×** over fp64 at n = 4M — almost all of it **bytes**, one per element against fp64's eight. The instruction's share looked like 1.42× from that machine alone (native `u8×i8` against emulated `i8×i8`, same run), but those two arms also take **different decompositions**: on the i7, where *both* are decomposed, the same pair still differs by 1.17×, putting the instruction at **~1.2×** net. Nothing in the Zen 4 data could have exposed it, and the claim stood for a day before the control arrived. The i7 also retires the 2013 Xeon as the bandwidth control — reaching 15.4× at n = 4M **without a usable VNNI instruction** is the clearest statement of the finding. §7 records the capability fact behind that: the i7 *has* AVX-VNNI silicon and MTL5 cannot reach it, because Highway implements the quad accumulate only in its AVX3_DL target, gated on AVX-512 macros Alder Lake does not have. Adds the hardware expansion plan — nine candidates written as experiments rather than a shopping list
- **The int8 GEMM claims are now measured on four machines, and the single-machine ones did not survive** (#470). #469 concluded from the Xeon alone that the quad kernel is worth "~1.25×" and that a VNNI purchase would be "buying something we already have". Both were wrong. The kernel effect ranges **1.27×–3.64×** — the Xeon is the low outlier by about a factor of three — and only the machines *with* the instruction beat fp32 by a margin worth having: the two decomposed parts land at 1.01× and 1.09× — beside fp32, not below it — while the two native parts reach 2.20× and 3.29×. The `native ÷ emulated` ratio is a **raw pairing ratio**, not the instruction's contribution: the pairings differ in signedness and decomposition path too, and netting the shape control (1.28× Xeon, 1.10× i7, measured where *both* pairings are emulated) puts Zen 4 at **1.74–2.02×** and the Jetson at 2.64–3.06×, the control acting in opposite directions because the machines implement opposite pairings. Against ~1.2× for the same instruction on a *dot*, this is the prediction the hardware plan made in direction and could not size — a dot is bandwidth-bound so instruction efficiency barely shows, a GEMM is compute-bound and shows it fully. The `best int8 ÷ fp32` column carries no pairing confound, comparing each machine's fastest int8 arm against its **own** fp32 GEMM, and is the one to quote when justifying hardware
- **The within-machine control for the instruction already existed.** The hardware plan said measuring it alone needs an AVX10.2 part or a Highway AVX-VNNI path, since forcing a decomposed Zen 4 build also drops AVX-512. Partial support **is** the control: native and emulated arms run in the same binary, on the same machine, in the same run. It is a control and not a clean one — the decomposition-path residue remains, which the fully-decomposed machines measure directly — so an ARM part that emulates *both* pairings is now worth as much as an AVX10.2 one

### Performance

- **`mc` is bounded at runtime by the strip of C the ic block accumulates into** (#457, #459). The L2 model sizes `mc` so the packed A block fills half of L2 and counts nothing else, while the same cache simultaneously holds that C strip. The obvious repair — adding the C term to the **compile-time** model — is falsified by its own calibration point rather than by a measurement: with *n* unknown there the strip must be `mc × nc`, and reproducing the shipped `mc = 64` then needs `mc·(kc+nc)·sizeof ≤ 8.5·L2`, which is not a residency statement, and the `nr = 4` family needs 2.5 rather than 8.5. What survives is the same idea in the right place — the strip is `mc × min(n, nc)` and *n* is known **at the call**, which is already where `mc` is capped for the thread budget
- **A is not charged against that budget, and the measurement decided it** (#459). Charging A+C fires whenever the pair exceeds L2, but on a Xeon E5-2420 (3 arms × 6 rounds, one session, with `mconly` holding as a null control) every **win** was a shape where C *alone* exceeded L2 (2048², 4096²: 1.151×, 1.158×) and every **loss** was a shape where C already fitted and the bound shrank `mc` for nothing (1024², 96×4096: 0.854×, 0.832×). A is streamed into the packed buffer and consumed once per jc block; C is read-modify-written across the whole kc loop and is the operand that has to stay resident. Shipped **off**, as the `ccap`/`ccap2` benchmark arms, so the bound is measured before it is adopted; #453 is falsified and #458 opened
- **The A/B analyzer was hiding a 15% effect and blaming the machine for it** (#459). It decided two arms were "identical" from their *configured* `kc`/`mc`, which are the same for all three arms on that machine — so it reported "null (identical blocking)" **and** raised an integrity failure against the same points. Identity now means the arms ran the same **plan** (`mc_used`, `ic_nt`, `jc_nt` per point, from #448), which is what it always meant to say; CSVs predating `mc_used` fall back to the old comparison, and every known case was re-verified

### Fixed

- **A GCC 13 miscompile on AVX2 integer reductions** (#460). The four interleaved accumulator chains are legal to reassociate on integers, and GCC 13 fuses them into one contiguous reduction while advancing three of them at half the required stride — silently wrong for **176 of the first 299** compile-time-constant lengths, `int32`/`uint32` only, Clang unaffected. Caught by CI's FP-contract lane; the emitted assembly accounts for the wrong value bit for bit. Integer reductions now run **one** accumulator, which is the right shape for them anyway — the loop-carried dependency is a 1-cycle add, so there is no latency to hide — and the floating-point path is byte-identical, verified
- **Strided vectors reached the contiguous fast paths** (#460). `strided_vector_ref` supplies `data()` and `size()`, which is all `BlasDenseVector` asked for, so **ten operations** accepted it and walked `data()` with unit stride: `dot_real` over a stride-2 view returned 14 where the answer is 44. This affected `float` and `double`, predates the integer work, and a column of a row-major matrix is exactly such a view
- **Integer overflow was undefined behaviour in the generic dense loops** (#460) — the path an integer `mult` takes in the **default** build, since `MTL5_NATIVE_FAST_GEMM` is off. The wrapping helpers were also not performed wide enough to be defined: integral promotion sends anything narrower than `int` to *signed* `int`, so `uint16` operands overflowed it, reachable as `dot_real` over a `dense_vector<int16_t>`
- **Shell scripts checked out with CRLF on Windows and could not run under WSL** (#466). There was no `.gitattributes` at all, which CLAUDE.md's cross-platform rules already required, so **all fifteen** tracked shell scripts were affected — `preflight.sh`, every `run_*` harness and every machine profile — meaning no part of the benchmark contract could be executed from a Windows checkout. `*.sh`/`*.bash` are pinned to `eol=lf`; `*.ps1`/`*.bat`/`*.cmd` keep CRLF since they only run on Windows; `.mtx`/`.csv` are pinned explicitly because the IO tests compare fixtures byte for byte. Repository content is unchanged (`git add --renormalize .` stages nothing) — only checkout behaviour, which is the whole defect
- **Undefined behaviour in the quad pack** (#469). Both pack routines hoisted a source pointer out of the padding guard, forming `A + (i0+i)·rs` for rows past the end of the source. The value is never loaded, but *forming* the pointer is already undefined. Neither sanitizer catches this — ASan sees no bad load because there is none, and UBSan's `pointer-overflow` check tests wraparound rather than escape from the object — so UBSan runs were clean before and after; it was found by reading
- **`mult_quad`'s documented generic fallback was a hard compile error** for any `Matrix` without an `orientation` alias (#469). `interface::is_row_major_v<MC>` was named at function scope, outside any discarded branch, and the concept does not require that alias — `compressed2D` and `transposed_view` both lack it — so the path that existed to keep the function "always correct, never merely fast" could not be reached by the types it existed for

## [5.10.0] - 2026-08-17

A benchmarking-infrastructure release, and the experiment it was built to run.
Two breaking changes, both narrow; see **Breaking** below before upgrading.

### Breaking

- **`Field<T>` is now false for integral `T`, and the factorizations require it** (#450). `lu_factor(dense2D<int>)` used to compile and return a **truncated factorization** — right shape, right type, wrong numbers, no diagnostic. `Field` asked only that `a / b` compile and yield a `T`, which `int` satisfies, so every algorithm meaning *"I will divide and expect the quotient back"* accepted a type that cannot give it one. ℤ is a ring, not a field: only 1 and −1 have inverses. `Field` now excludes `std::is_integral` types, the new `FieldMatrix` applies it, and the **25 entry points that divide** — LU, QR, LQ, Cholesky (real + Hermitian), LDLᵀ incl. Bunch-Kaufman, SVD, eigen (general + symmetric), `inv`, factor and solve alike — require it. Integers keep `Scalar`, which is the honest statement: they add and multiply, so dot/gemv/gemm remain open to them (a ring is all those need). Custom number types are unaffected — posit, LNS, fixpnt and rationals are not `is_integral`. **What breaks downstream:** `vec<int> / 2` and integer matrix/scalar division, deliberately, since truncating division is the same hazard one level down
- **Runtime cache detection is opt-in and off by default** (#433). Introduced in #426 on the assumption that real cache sizes must beat constants tuned for a Haswell-class core, it **lost** on every machine measured. Enable with `MTL5_ENABLE_CACHE_DETECTION` if you want to evaluate it on your own hardware; the shipped blocking is byte-identical to pre-#426

### Added

#### A measurement contract for every benchmark (#442)
Each guard below was added *after* the matching error had already produced a number someone believed — a Zen 4 run that deleted the i7's committed CSVs, an analyzer that called a 4.8% "win" between byte-identical arms, a Jetson that asked for eight threads on a six-core part. The contract is the first layer written before the error rather than after it.
- **`benchmarks/preflight.sh` / `.ps1`** (#444) — runs before any measurement and **fails**, not warns, on a dirty working tree, a competing build or benchmark, or a thread count above the available cpus. Emits `key=value` machine state either way, so it lands in the sidecar rather than in the operator's memory of the session. The thermal gate fails **only where a sensor and a limit are both readable** — Windows desktop firmware usually implements neither, and refusing to run there would make the machine unbenchmarkable while passing silently would hide the gap; it records `unavailable` out loud. Governor is recorded and warned about, never failed: every machine in `systems.md` runs a non-performance governor, and a hard gate would block all of them
- **Build provenance in every sidecar** (#443) — `git_commit`, `git_dirty`, `cxx_flags`, `cmake_type`, regenerated at **build** time rather than configure time, so a sidecar cannot name a commit it was not built from. Plus **`build_isa`** (`mtl::util::build_isa_list`), read from the compiler's own predefined macros: `cxx_flags` is the build's *intent* and can omit the flag that mattered (`MTL5_NATIVE_ARCH` adds `-march=native` through `target_compile_options` and appears in no `CMAKE_CXX_FLAGS` variable), while `build_isa` is the *effect*. This is what finally answered whether a Zen 4 session had been AVX-512 or AVX2
- **The plan the GEMM nest actually runs** (#448) — `detail::gemm_plan_for<T>()` returns `mc`, `nib`, `njb`, `ic_nt`, `jc_nt`, `budget`, and `gemm_blocked` now *uses* it rather than recomputing the same three steps inline. Benchmarks record `mc_used` per point, so the parameter under test is in the record of the experiment testing it: three stages separate the configured `mc` from the one the loops step by, and the CSVs previously reported the first
- **Four selectable A/B arms** (#449) — `default`, `detected` (L1+L2), `kconly` (L1 → kc), `mconly` (L2 → mc), all the same source, run in **one session** with the order rotated per round. `with_detected_caches` takes the levels as an argument rather than reading macros, so every combination is unit-testable without recompiling
- **Per-machine run profiles** (`benchmarks/machines/`) — the pin list, thread counts, ISA flag and output directory for the i7-12700K, Jetson Orin Nano and Ryzen 9 8945HS, committed instead of retyped. Each **refuses to run on a machine it does not recognise**, since the CSVs are named by arm and the runner clears them before writing. The Jetson's output directory follows its `nvpmodel` power mode, because a 15 W run and a MAXN run are not comparable and one directory is how they would end up averaged
- **`mtl::util::build_isa_list()`** (`util/system_info.hpp`) — the ISA the binary was compiled for, distinct from `cpu_simd` (what the machine supports). Emitted as `build_isa=` in every sidecar
- **The integer accumulation envelope, measured** (`tests/unit/simd/test_int_accumulation.cpp`) — how deep an integer dot product can go before an `int64` accumulator overflows, as a contract test rather than a rule of thumb. ≤16-bit operands are safe past a million terms in both the zero-mean and the offset regime; only full-range operands genuinely fail. Portable by construction: a product of two `int32` always fits an `int64`, so only the running sum can overflow and checked addition detects it without `__int128`

### Fixed
- **The GEMM thread grid is planned, not greedily filled** (#441). `ic_nt` was taken as `min(budget, nib)` and `jc_nt` as the integer quotient, which throws the remainder away: at budget 6 with `nib = 4` that is 4×1 = 4 of 6 threads, and with `njb = 1` (square problems) no `jc` parallelism compensates. `plan_gemm_grid` searches the legal factorizations and also caps `mc` so the ic partition can fill the machine. Measured: i7 1024³ at 8 threads 0.551 → 0.707, Zen 4 0.590 → 0.928, Jetson 0.760 → 0.938 relative to the shipped blocking
- **Cache detection is deterministic and shared-cache aware** (#436) — per-core budgets divide by the number of cores sharing a level, and SMT siblings no longer halve L1d/L2
- **Preflight no longer fails on the harness's own output** (#447) — the PowerShell driver builds before it measures and wrote its cmake logs beside the CSVs, so the run tripped over files it had just produced. Logs are gitignored, the dirty check excludes the harness's own `OUTDIR` (contained to `benchmarks/data/<machine>` so it cannot become a hole through the gate), and `-AllowDirty` exists because `set ALLOW_DIRTY=1` is cmd.exe syntax that silently does nothing in PowerShell
- **A per-machine `OUTDIR` is required, with no default** (#439) — the CSVs are named by arm and the runners delete them before writing, so a shared default destroys another machine's committed results. Which is exactly what happened once
- **The effective thread pool is recorded** (#440) — `thread_pool` clamps `MTL5_NUM_THREADS` to `hardware_concurrency`, so a request of 8 on a 6-core part measured 6 while the CSV said 8; the `pool` column records what ran
- **`CMakePresets.json` lowered to schema v3** so CMake 3.22 can read it (#435)
- **A wall-clock ratio no longer gates every PR** (#454). `sparse_test_native_klu` asserted `time_ratio < 13.0` on a ratio of two single timings, in the fast tier, on shared cloud runners — it failed on macOS on a PR that changed no C++ at all (14.997), and sampled three times on an *idle* machine the statistic itself moved 31% (5.24, 5.91, 6.87). Nothing algorithmic was lost by removing it, because the same test already asserts `fill_ratio < 8.0`, and fill is the **deterministic** observable of the same property: a sparse factorization's asymptotic cost is driven by fill growth, and the clock measures fill plus noise. The timing claim moves to `tests/regression/sparse/test_klu_scaling.cpp` in a **stricter** form — minimum of 3 samples per size, both refinement steps checked rather than only the last, and a floor requiring the baseline to exceed 1 ms so the ratio cannot degenerate into a timer-resolution artefact. The unit test drops from **10.19 s to 1.49 s**. `regression_itl_test_gmres` also gets the 600 s timeout `cg` and `bicgstab` already had: at 8m06s on a Xeon E5-2420 v2 it timed out at the 300 s default, making the regression tier unrunnable locally on any machine slower than a CI runner

### Performance
- **`run_scaling` and `run_sweeps` build every variant before measuring any of them** (#445) — each backend used to be built and then immediately measured, so every arm was timed on a machine still hot from compiling its own binary while the next compiled during the previous one's cooldown. MKL's `setvars.sh` is now sourced in a subshell for both configure and run, so oneAPI's `LD_LIBRARY_PATH` cannot leave the openblas and blis binaries resolving MKL's libraries while still labelled as themselves

### Changed
- **Performance studies are a top-level documentation section** (`docs/performance/`), lifted out of Design: they answer "what did the machine do", not "how is it built"
- **[Cache blocking A/B](docs/performance/cache-blocking-ab-study.md)** — the four-machine experiment written up with its hypothesis, exact sign and permutation tests, identical-binary calibration and verdict. The headline: **raising `mc` is the harm and it is visible with one thread; raising `kc` is free serially.** The earlier conclusion, which had it backwards, is corrected in place. Neither parameter is ever a win, which is why detection ships off
- **The analyzer fails identical-parameter arms that disagree systematically** — arms sometimes collapse onto each other (on Zen 4 `kconly` *is* `default`), and those pairs measure the session rather than the code. It disqualified a Jetson session whose round-to-round spread was larger than the effect under test
- `ROUNDS` is rounded up to a multiple of the arm count, so the rotation balances exactly

## [5.9.1] - 2026-08-13

### Performance

- **Sparse LU refactor 23% faster via `sparse_lu_refactor_in_place` / `supernodal_lu_refactor_in_place`** (#310). The reported defect was real: `*_refactor` installed through `set_factor`, which unconditionally rebuilds both level-solve schedules, even though a same-pattern refactor leaves `col_ptr`/`row_ind` byte-identical and the schedules are **value-agnostic** — they cache positions into the factor's value arrays, not the values. But fixing exactly that measured **~2%**. The value-returning API copies `prev`, and copying the schedules (two `nnz`-length `size_t` arrays each) costs about what rebuilding them costs, so removing the rebuild *moved* the O(nnz) work rather than removing it. The win needed the copy gone too: the in-place entry points replay the values on the installed pattern and install them without copying pattern, schedules, or permutations. Measured on a 6400-DOF 5-point grid (`nnz(L)+nnz(U)` = 390K, GCC -O2, min of 5 runs): **26.3 → 20.3 ms/refactor**, with markedly lower run-to-run variance since no large allocation remains on the path. `sparse_lu_refactor`/`supernodal_lu_refactor` keep their signatures as "copy `prev`, refactor in place", and `native_klu_refactor` inherits the change through its per-block call
  - **`set_factor_values`** (`lu_numeric`, `supernodal_lu_factor`) is the validated value-only install: it requires a factor already installed and re-checks the value counts against both the installed `nnz` **and** the schedules' `built_nnz` staleness guards — the same guards the solves assert on — so a pattern change cannot slip through silently. `set_factor` remains the entry point for that. The install is ordered first in both refactor paths because every member update after it is noexcept, which gives the whole operation a strong guarantee: values are computed into scratch arrays and installed only after the last column succeeds, so a zero pivot leaves the factorization untouched and still solvable with its previous values (asserted, not assumed)
- **Wide/short dense-matrix expressions now parallelize at all** (#313). The `dense2D` expression sweeps (ctor / `=` / `+=` / `-=`) made each **row** one `parallel_ewise` work unit, and `thread_pool::parallel_for` runs serially when `n < grain*2` — so a `1 x 300000` assignment had `n == 1` and could never split, however much work the row held. Same wide-shape gap #311 closed for GEMM. `detail::parallel_ewise_2d` flattens `(r, c)` to a linear element index `[0, rows*cols)` **before** chunking, so the split follows the element count and `1 x N` parallelizes exactly like `N x 1`. Two things worth stating because the obvious implementation gets them wrong: each chunk walks `(r, c)` incrementally from a single division at its start, so the per-element cost is an increment and a compare rather than the `t / cols`, `t % cols` a per-element decomposition would pay; and `work_per_elem = 1` yields `grain = 65536` **elements**, exactly the chunk size the row form's `65536 / num_cols` rows produced, so tall matrices see identical splitting behaviour and only the boundary alignment changes (row-aligned → element-aligned), which element-wise results cannot observe. Bit-identity holds by construction — row-major visit order is unchanged, each element is produced by exactly one chunk, and the per-element computation is thread-independent — and is asserted with `==` on wide shapes through all four sweeps. The split itself is **observed rather than inferred**: a probe expression records which thread evaluated each element, an assertion that fails on the row-per-unit sweep (`1 > 1`). TSan clean at `MTL5_NUM_THREADS=4`. The second half of #313 — the ~K× too-coarse grain for the opt-in lazy `mat_mat_times_expr`, whose `operator()(r,c)` is a length-K inner product — is split out to #424, since it needs a public per-element work-hint trait

## [5.9.0] - 2026-08-07

### Added

#### Complex (Hermitian) dense factorizations (#353)
`cholesky`, `qr` and `lq` did not compile for `std::complex`, failing first on relational operators applied to a complex where a *magnitude* was meant. Repairing only those comparisons would have produced routines that compile and compute the **wrong** result, by a different mechanism in each: `cholesky`'s unconjugated inner product yields `L·Lᵀ` rather than the `L·Lᴴ` a Hermitian matrix has, while `qr`/`lq` additionally need `Σ|z|²` in place of `Σz²` and a reflector written `I − τ·v·vᴴ` rather than `I − β·v·vᵀ`. Neither fix repairs a comparison.
- **`mtl::cholesky_h_factor` / `mtl::cholesky_h_solve`** (`operation/cholesky.hpp`) — `A = L·Lᴴ` for Hermitian positive definite input. The pivot is accumulated in the **magnitude** type rather than the element type, which is what makes the positivity test well-formed: an ordering is exactly what the element type lacks. Rejects a non-real diagonal with `CHOLESKY_NOT_HERMITIAN`. `cholesky_factor` is now restricted to real element types with a diagnostic naming the alternative — unlike `ldlt` there is no complex-symmetric variant to offer, since "positive definite" is a statement about an ordering (#360)
- **Complex Householder, QR and LQ** (`operation/householder.hpp`, `qr.hpp`, `lq.hpp`) — the reflector is now `H = I − τ·v·vᴴ` with `H·x = β·e₁` and β real, built as in LAPACK `zlarfg`. `H` is unitary but **not Hermitian** for complex τ, so `H⁻¹ = Hᴴ`; that lands as `conj(tau)` in `qr_extract_Q`, plain `tau` in `lq_extract_Q`, and a conjugated row plus `Hᴴ` on the LQ factor side. Verified `‖QᴴQ−I‖ ≤ 7.8e-16` and `‖QR−A‖ ≤ 7.0e-16` over square, tall and wide shapes (#361)
- `hessenberg_factor` and `eigen_symmetric` now **reject** complex element types. They apply `H·A·H`, a similarity transform only because a real reflector is Hermitian and involutory; making `householder()` complex-capable would otherwise have let them compute a non-similar matrix. The Hermitian reduction is tracked in #362 (#361)

#### Hermitian eigenproblem — unitary reduction (#362)
The guards above are lifted. `hessenberg_factor`/`hessenberg`/`tridiagonalize`, `eigenvalue_symmetric`(`_generic`) and `eigen_symmetric` now accept complex element types via the **unitary** reduction `A → H·A·Hᴴ` — the right factor passes `conj(τ)` to `apply_householder_right` (the same adjoint bookkeeping #361 worked out for `qr_extract_Q`), a genuine similarity since `H⁻¹ = Hᴴ`. For a real element type `conj` is the identity, so every real path stays **bit-identical**: the QR-iteration scalars are typed `magnitude_t<value_type>` (which *is* `value_type` there), and eigenvalues come back as that magnitude type (real for Hermitian).
- **The phase, and where it is actually exercised.** A Hermitian tridiagonal has a real diagonal but phased subdiagonals; making them real is a diagonal unitary similarity `Dᴴ·T·D` that preserves the spectrum, so `eigenvalue_symmetric` needs only `|T(i+1,i)|` while `eigen_symmetric` folds `D` into the eigenvectors so `A·v == λ·v` (skip it and the eigen**values** still look right — the silent-wrong shape #352/#353 kept hitting). But MTL5's `householder()` reflects to a **real β**, so for `n ≥ 3` the reduction yields real subdiagonals *for free* and the fold is a no-op ±1; the phase is genuinely complex only when the reduction is **skipped** (`n < 3`), where `T(1,0)` is the original off-diagonal. The `2×2` tests (`[[2,i],[-i,2]]`, and an off-axis `[[1,1+i],[1-i,2]]`) are therefore the cases that *pin* the fold — drop it and their eigenvectors come back real and fail the residual
- **The #361 guard had been covering nothing.** It sat on `eigenvalue_symmetric_generic`, which never calls `householder`; the compile-failure test matched its regex and passed while the actual reduction site, `eigen_symmetric`, stayed open. The two compile-failure pins are retired and the reduction site is what the new tests exercise. Invariants asserted self-consistently (no LAPACK dependency): real eigenvalues, `A·v == λ·v` per pair, `Qᴴ·Q == I`, and the reconstruction `V·diag(λ)·Vᴴ == A` — the check that catches a *non-similar* reduction, which a merely-unitary `Q` does not (#361's lesson). `eigenvalue_symmetric_generic` also gained a `0×0` guard before its `e(n-1)` sentinel write

#### LAPACK Hermitian eigensolver + native cross-validation (#415)
- **`cheev`/`zheev` bindings** (`interface/lapack.hpp`) and a **`BlasHermitianMatrix`** concept (`interface/dispatch_traits.hpp`); `eigenvalue_symmetric` routes a complex Hermitian matrix to `heev` under `MTL5_HAS_LAPACK`, mirroring the real `syev` path. Eigenvalues `W` are real, `heev` takes an extra real `rwork` of length `max(1, 3n−2)`, and the optimal `lwork` returns in the *real part* of the query's `work[0]`
- This gives the native complex reduction a **reference oracle**. The self-consistent #414 invariants catch a *phase* bug but not an algorithm that is self-consistently wrong; `test_lapack_dispatch` now cross-checks `eigenvalue_symmetric_generic` (native) against `zheev` and they agree to `1e-9` on known, degenerate (`{2,2,2,10}` from `2I + v·vᴴ`), and dense spectra

#### LAPACK dispatch for the default (row-major) matrix type (#417)
`dense2D` defaults to `tag::row_major`, and every LAPACK factorization/eigensolver dispatch guarded on `!is_row_major_v<M>` — so the **default matrix type never took the accelerated path**, and the pre-existing real `syev`/`geev` "dispatch" tests were silently running the generic path. Invisible because both paths return correct answers; the only decisive check is a **symbol assertion** — a row-major-only translation unit referenced *no* LAPACK symbols before and `dsyev_/zheev_/dgeev_/dgesdd_` (+ `dgetrf_/dgeqrf_/dpotrf_`) after.
- **Category A — the guard was redundant (#418).** `eigenvalue_symmetric` (`syev`+`heev`), `eigenvalue` (`geev`) and `svd` (`gesdd`) already build a column-major copy *through the `(i,j)` accessor*, so they are correct for either orientation; dropping `!is_row_major_v<M>` enables LAPACK for the default type at zero correctness risk
- **Category B — the guard was load-bearing (#419).** `lu`/`qr`/`cholesky` pass the raw `A.data()` buffer to Fortran, where a row-major buffer is the *transpose* of what LAPACK reads. Row-major now factors through a column-major scratch (copy in via `(i,j)`, LAPACK in place, copy the factor back via `(i,j)`), so the accessor-based solves read it unchanged. `cholesky_h_factor` **delegates to `cholesky_factor`** for real BLAS types — `L·Lᴴ` *is* `L·Lᵀ` there — which keeps the two entry points bit-identical (an invariant `test_cholesky.cpp` pins with `==`, which independent factoring would break once `cholesky_factor` uses `potrf`). A zero-dimension guard was added to all three (LAPACK rejects `lda == 0`)
- **The `#297` determinism tests move to a non-BLAS type.** They assert the threaded factorization is bit-identical to a serial *generic* reference — a property of the `parallel_for` kernel, not of LAPACK. Since the default `double` path now dispatches to LAPACK (a different algorithm), the LU/Cholesky determinism cases switch to `long double` (never `is_blas_scalar`), so `dense2D<det_t>` keeps exercising the generic parallel path in LAPACK and non-LAPACK builds alike; the `apply_householder_*` cases stay `double`, since those kernels never dispatch

#### Sparse × sparse product (SpGEMM)
- **`mtl::spgemm(A, B)`** (`operation/spgemm.hpp`) — Gustavson's row-by-row algorithm over the existing sparse accumulator (`sparse/util/scatter.hpp`, CSparse's `cs_scatter`), so work is proportional to the multiply-adds actually performed rather than `n³`. `compressed2D * compressed2D` previously fell through to the generic dense `operator*`, which both materialised an `n × n` dense intermediate *at the fine-grid size* and reached every element through `compressed2D::operator()(r, c)` — itself a binary search. The Galerkin triple product `A_coarse = R·A·P`, the one product a multigrid user most needs to stay sparse, was the one that did not. `operator*` on two `compressed2D` now returns `compressed2D`; verified before the change that no call site multiplied two sparse matrices, so nothing relied on the dense result. Single pass, no separate symbolic phase — that buys exact sizing and a reusable pattern only when the *same* structure is multiplied repeatedly, and multigrid setup builds each level once. Entries that cancel to exactly zero are kept, so a Galerkin hierarchy's pattern is stable across re-assembly (#402)
- The gathered indices are **sorted** before being written, because `compressed2D::operator()` uses `std::lower_bound` and ascending column indices are therefore a correctness invariant rather than a convention. Worth stating how invisible skipping it would be: measured with the sort removed, `nnz` is correct, row sums off the raw CSR arrays are correct to 4.4e-16, and a sparse matvec is correct *to rounding* — it sums `data[k]*x(indices[k])` over whatever order the row is in, and reordering preserves the set of products, so the sum is still right (not bit-identical, since floating-point addition is not associative, but wrong at eps rather than at all) — while element access is wrong by 3.2 absolute. The natural tests for a matrix product all pass on the corrupt result, so `test_spgemm.cpp` asserts the index structure directly instead of trusting a residual (#402)

#### Compile-failure test harness
- **`tests/unit/compile_fail/`** — sources that must *not* compile, built on demand by ctest (`EXCLUDE_FROM_ALL`) so ordinary builds are unaffected. Each declares an `// EXPECT-ERROR: <regex>` line and is matched with `PASS_REGULAR_EXPRESSION` rather than CMake's `WILL_FAIL`, which passes on *any* non-zero build exit and would go green on a typo in the test source. The distinction is not theoretical: removing the `cholesky` guard leaves the file still failing to compile via the old `operator<=` error, so `WILL_FAIL` would have been green while the regex catches the regression to the worse diagnostic (#358)

#### Platform Performance Engineering lab
- **`ppe/`** — a progression of GEMM implementations (naive → loop order → blocking/packing → register tiling → compile-time microtile) measured across `int8/16/32/64` and `fp16/32/64`, with hypotheses recorded before the experiments that test them. Documents the *vectorization cliff*: the compile-time-unrolled microtile is **5× slower** than a plain loop reorder for `fp32`, because full unrolling removes the loop structure the vectorizer needs and 32 scalar accumulators then spill — while being the *best* kernel for `int32`, whose SIMD headroom is small (#354)

### Fixed

#### Preconditioned Krylov solvers: three defects behind one blind spot
All three were invisible to the existing tests for the same structural reason: every preconditioned `bicg`/`qmr` case used `pc::identity`, the one preconditioner for which applying `M⁻¹` twice, or on the wrong side, or with the wrong adjoint, is indistinguishable from applying it once correctly. `tests/unit/itl/test_preconditioner_adjoint.cpp` now asserts the *defining* property — `⟨M⁻¹b, c⟩ == ⟨b, M⁻ᴴc⟩` — which is exact, cheap, and found two defects the reporting issue had not identified.
- **`bicg` computed `rho` from `z̃ᵀz` instead of `zᵀr̃`**, i.e. from two preconditioned vectors rather than one preconditioned and one raw. With a non-trivial preconditioner it converged to the wrong scaling or not at all; with `pc::diagonal` on a 144×144 SPD Laplacian it hit the 3000-iteration cap where `cg` took 33. Preconditioned BiCG reduces *exactly* to preconditioned CG when **both `A` and `M` are SPD** — the symmetry of the preconditioner is a separate requirement from that of the system, and is what makes the reduction hold — so the fix is asserted that way against `pc::diagonal`, which is symmetric whatever `A` is: same iteration count, not merely convergence (#392)
- **`qmr` applied the preconditioner twice, once on each side**, rather than the Freund–Nachtigal split `M = M₁·M₂` with `M₁ = M`, `M₂ = I`. The algorithm needs `w̃ᵀM⁻¹ṽ`; the old code produced `M⁻¹` on both the shadow and the primary vector. Fixed at the update sites, with `q` built from `z̃`. QMR minimizes a *quasi*-residual so it does not reduce exactly to CG; the test asserts it tracks within two iterations rather than pinning a coincidence of stopping criteria (#393)
- **`pc::ilu_0` and `pc::block_diagonal` had `adjoint_solve` stubs that delegated to `solve`**, which is correct only when `M` is self-adjoint. `M = L·U` is not, and a diagonal *block* of a non-symmetric `A` is not either, so `bicg`/`qmr` applied the wrong operator outright and did not converge at all. `ilu_0` now does `U⁻ᴴ` then `L⁻ᴴ` in scatter form over the existing row storage; `block_diagonal` routes each block through the new public `mtl::lu_adjoint_solve` (`operation/lu.hpp`), which applies `Uᴴ` forward, `Lᴴ` backward, and the inverse permutation as the same interchanges in reverse. `ic_0` and `ildl` were checked and are correct *by construction* — `L·Lᴴ` and `L·D·Lᵀ` are self-adjoint — so delegation there is right rather than lucky (#394)

#### Other
- **`itl/mg/multigrid.hpp` was not self-contained.** It used `mat::operators.hpp` without including it and compiled only because every existing consumer happened to include it first — `test_multigrid.cpp` supplied it at line 7 of a 16-line include list. A new translation unit including only `multigrid.hpp` failed. Added the include, plus `test_multigrid_self_contained.cpp`, whose include list is load-bearing and labelled as such so it is not "tidied" later (#401)
- **`fast_gemm`'s numeric test compared against a `long double` reference**, which is 80-bit on x86-64, 64-bit on Apple ARM64 and MSVC, and 128-bit on ARM64 Linux — so the *assertions inverted* by platform. Replaced with a portable double-double reference (Knuth two-sum + exact two-product via FMA, ~106 bits). The tolerance is now stated as **empirical** rather than derived: `4·k·eps` is not a tightening of a `k·eps` worst case, it is 4× wider, and the true worst-case relative error against the test's `(|ref|+1)` denominator is nearer `k^1.5·u` (#386)
- **`pc::ssor` applied the wrong operator**, because its sweeps started from `x = b` instead of `x = 0`. A stationary iteration and a preconditioner are the same splitting matrix `M` viewed two ways, and applying `M⁻¹` means running one sweep *from zero*; from any other start the result is `M⁻¹b + G·x₀` with `G = I − M⁻¹A` — fine for a solver, where the initial guess is arbitrary, wrong for a preconditioner. Run from zero the two sweeps are *exactly* the classical operator `M = ω/(2−ω)·(D/ω + L)·D⁻¹·(D/ω + U)` (Sheldon 1955), scalar factor included, so sweeps and triangular solves are the same operator rather than two competing formulations — now asserted against a dense LU of `M` at two ω. For Hermitian `A` that is `c·X·D⁻¹·Xᴴ`, self-adjoint by construction, which is why the symmetric variant exists at all; the adjoint identity violation goes from **1.1e-01 to 3.4e-16** and `adjoint_solve`'s delegation to `solve` becomes correct rather than a stub. On a symmetric 144×144 Laplacian every solver improves: cg 16 → **13** iterations, gmres 13 → **12**, bicg 16 → **13**, qmr 16 → **13**. SSOR of a non-Hermitian `A` remains non-self-adjoint (2.6e-01) — a property of the method, now asserted so it is not mistaken for a residual bug. The one configuration that gets *worse* is `cg` + `ssor` on a **non-symmetric** `A` (45 iterations → does not converge), which is outside CG's domain in the first place: its former convergence rested on the extra `G_B·G_F` term, not on the preconditioner (#398, #394)
- **`ldlt` returned a wrong answer for Hermitian complex input** under `info == 0`. Added `ldlt_h_factor` / `ldlt_h_solve` for `A = L·D·Lᴴ`, and guards in both directions: `LDLT_NOT_SYMMETRIC` when Hermitian input reaches the LDLᵀ form, `LDLT_NOT_HERMITIAN` when a non-real diagonal reaches the LDLᴴ form. Both tests are **scale-relative** (`n · eps · scale`, via LAPACK's `CABS1` to avoid an O(n²) sweep of `hypot`), because an exact test only catches matrices that are bit-exactly Hermitian — a one-ULP perturbation slipped past the first version and produced an answer wrong in the first significant digit. Shared thresholds live in `detail/structure_tol.hpp` (#352, #356)
- **`compressed2D` accepted `tag::col_major` and ignored it.** The container is CSR unconditionally, so a `col_major` instance was byte-for-byte a CSR matrix and genuine CSC input came back as its **transpose** while the constructor reported success. Now rejected at compile time; `ell_matrix` carried the same inert-orientation hole and is rejected too. `coordinate2D` is deliberately untouched — it stores explicit `(row, col, value)` triplets, so orientation cannot change a result (#355, #358)
- **`householder` broke its own real-β guarantee** for a complex vector with a vanishing tail and a complex leading entry, returning `tau = 0` and leaving a complex `R`/`L` diagonal — silent, since `Q` stayed unitary and `Q·R` still reproduced `A`. The identity shortcut is now taken only when it is exact (#361)

### Performance
- **Multi-core GEMM +27% at N=1024 and +10% at N=2048 on 8 P-cores**, recovering the scaling regression #382 introduced (#408). The cause was not cache pressure from the larger register tile, as first supposed, but that `mc` was rounded down to a multiple of `mr` — coupling a **cache** quantity to the **register tile**. The L2 budget yields exactly 64, which survives `mr=4` but drops to 60 under #382's `mr=6`; that moved the ic-block count at m=1024 from 16 (exactly 2.00 blocks per thread on 8 threads) to 18 (2.25), and since the threaded nest hands ic-blocks out round-robin, the most-loaded thread went from 128 rows to 180 — a **1.41× critical path** that turned a +21.5% single-thread win into a −7.4% eight-thread regression. `mc` now derives from the cache alone, and `detail::balanced_mc` chooses the block size against `m` and the thread count at runtime, where both are known; the serial path still rounds to whole `mr`-panels, since with nothing to balance that is strictly better. Measured interleaved against the same session's baseline, three reps, ranges non-overlapping: parallel efficiency 62.7% → **81.8%** at N=1024 and 77.5% → **85.8%** at N=2048, with T=1 unchanged (−2.5%/−0.4%, overlapping ranges). The multiple-of-`mr` constraint was never a correctness requirement — `pack_A` already handles a ragged final panel, since `m` is not generally a multiple of `mr`
- **Blocked GEMM parallel efficiency 79% → 91%** on 8 physical cores. The shared B panel was packed by each jc-team's leader while the rest of the team waited on the barrier — a serial region proportional to `kc·nc` per `pc` step (at N=2048 with a team of 8, one thread packed ~67 MB while seven idled). The team now splits the NR-column panels; packing is pure data movement into disjoint offsets, so the packed bytes and the result are unchanged (#348)

### Changed
- **i7-12700K GEMM scaling re-measured a second time after #410** (2026-08-05). Multi-core throughput is now the highest recorded on this machine — 470.9 GFLOP/s at N = 2048 on 8 P-cores against 429.4 before #410 and 401.8 before #382 — and the −7.4% regression at N = 1024 is gone (+22.0%). **The "native-fast is the worst scaler" finding is softened, not withdrawn**: efficiency is 85.5%, up from 79.2% but still short of the pre-#382 era's 90.5% and last of the four backends. The single-threaded BLAS sweep was deliberately not re-run — `balanced_mc` only engages when `ic_nt > 1` — which gives a control: native-fast's `T = 1` figure moved 67.81 → 68.82, inside the ~4% session band

- **`pc::ssor` is now the adapter over `smoother::symmetric_sor` it was already documented to be** (#405). It had been an independent reimplementation of the same two sweeps — its own loops and diagonal cache, duplicated across a generic and a `compressed2D` specialization — while `docs/design/smoothers-architecture.md` described it as a wrapper. Since #398 established that one symmetric-SOR application from a zeroed vector *is* `M⁻¹b`, the preconditioner collapses to three lines over the smoother: **−129 lines**, and the matrix-type specialization comes from `smoother::sor` so the O(nnz) sparse path is inherited rather than restated. Two consequences beyond the line count: `pc::ssor` gains the `Accumulator` template parameter (defaulted to `void`, so a widening rather than a break) — mixed-precision *preconditioning* was previously impossible while mixed-precision *smoothing* worked, with nothing in the API saying so; and the class of bug fixed in #398 becomes unrepresentable, since the duplicate was where it lived. The smoothers' sweeps are now `const` (they only ever mutated the caller's `x`), which is what lets the preconditioner hold one as a member and still expose a `const solve()` without `mutable`. Operator and iteration counts are unchanged — the adjoint violation moves 3.432e-16 → 3.545e-16, a last-ulp shift from the smoother's reciprocal-multiply against the old divide

### Added
- **`mtl::math::accumulator_round_type<Acc, Mag>`** (`math/accumulator_traits.hpp`) — names the arithmetic type an accumulator should be rounded out to before a scalar post-processing step such as `sqrt`: the accumulator itself for a plain arithmetic `Acc`, `T` for `fma_accumulator<T>`, and the magnitude type for a custom/quire accumulator. Lets the sum-of-squares norms accept all three configurations of the accumulator model without narrowing the sum before the root, and requires nothing new of external specializations (#324)

#### Dense mixed-precision iterative refinement (BLAS extraction from Universal)
- **`mtl::lu_iterative_refine<Working>(A, b, x, opt)`** (`operation/lu_iterative_refine.hpp`) — the dense counterpart of `sparse::iterative_refine`: factor A once in a low `Working` precision via `lu_factor`/`lu_solve`, then correct with a residual formed in the (deduced, higher) `Residual` precision. Universal-free and generic over the arithmetic type. Shares the sibling's `refine_options`/`refine_result` shape: best-iterate return, patience for a noisy low-precision residual, `rel_tol` convergence, and an opt-in `scaled` (scale-and-round) variant that carries the correction magnitude in `Residual` precision so narrow-exponent `Working` factors don't underflow.
- **`mtl::normwise_backward_error(A, x, b)`** (`operation/backward_error.hpp`) — the normwise backward error `||b - A x||_inf / (||A||_inf ||x||_inf + ||b||_inf)` (Higham, "Accuracy and Stability of Numerical Algorithms", Thm 7.1), the natural quality/termination metric for refinement.
- Ported (Universal-free) from Universal's `blas/ext/solvers/luir.hpp` (`SolveIRLU`) + `blas/utes/nbe.hpp` as the first library piece of the Universal->MTL5 linear-algebra extraction; the posit/precision *experiments* driving it live in mp-ir (Universal epic #1204, phase #1207).

#### Range and test-matrix generators (BLAS extraction from Universal)

#### Matrix/vector/tensor property predicate module (#244)
A cohesive set of runtime property and predicate queries as free functions in `namespace mtl`, built on the existing primitives (cholesky/lu/svd/eigenvalue/norms) with no new dependencies. Consistent tolerance policy: structural checks are exact-by-default and NaN-safe (`!(dev <= tol)`), while norm/factorization/spectral-backed checks use relative or scale-aware tolerances; verified on both the in-house and LAPACK paths.

- **Factorization-backed predicates** (`operation/factorization_properties.hpp`) — `is_spd`/`is_positive_definite` (symmetric + Cholesky), `is_singular`/`is_nonsingular`/`is_invertible` and `determinant` (LU), each on a copy so the caller's matrix is unchanged (#246)
- **Spectral / condition / rank** (`operation/spectral_properties.hpp`) — `spectral_radius`, `condition_number`, `rcond`, `numerical_rank`, `nullity`, wrapping the dense SVD and eigensolver (#247)
- **Rank-2 tensor predicates** (`tensor/properties.hpp`) — `is_symmetric`, `is_antisymmetric` (#248)
- **Orthogonality + inertia** — `is_orthogonal`/`is_unitary` (`AᴴA == I`) and `is_normal` (`AAᴴ == AᴴA`), plus `inertia` (the congruence-invariant `(positive, negative, zero)` eigenvalue-sign triple, Sylvester's law) and `is_indefinite`; inertia is backed by the symmetric eigensolver so it is robust for singular/semidefinite inputs (#249)

#### On-node threading (#221)
- **`mtl::detail::thread_pool`** — a persistent worker pool (no OpenMP/TBB, just the C++ standard concurrency runtime) with `run`, `parallel_for` (bit-identical contiguous chunking), and `parallel_reduce` (chunked, deterministic-per-thread-count). Threading is **off by default**; `MTL5_NUM_THREADS` (read once, clamped to hardware concurrency) sizes the pool, and `=1`/unset creates no workers and runs the original serial paths (#239)
- **Threaded kernels** on the pool — blocked GEMM (#239), row-/col-major GEMV and `axpy`/`scal` (#240), `dot`/`nrm2` and column-major GEMV (#241), and sparse SpMV `compressed2D * vector` (#242). The iterative and eigensolvers inherit the SpMV/L1 threading with no solver-code changes. Every kernel except the reductions is bit-identical across thread counts
- **Documentation** — an on-node threading reference (`docs/algorithms/on-node-threading.md`) and a performance-engineering case study on multi-core scaling (`docs/design/multicore-scaling-investigation.md`), including the SMT-affinity measurement pitfall and the corrected 6.3–6.9× GEMM scaling on 8 physical cores (#243)

#### On-node threading — factorizations, triangular solves, multi-loop GEMM, element-wise (#297)
Extends the #221 pool from the BLAS kernels to **every substantial dense and sparse kernel**, each **bit-identical across thread counts** (the parallel result equals the serial one exactly, `==`, not to a tolerance) and serial-by-default. Rolled out in ten batches; validated per batch against the serial path and under ThreadSanitizer.
- **Dense factorizations** — parallel trailing/column updates in LU and Cholesky (#298); parallel Householder reflector application (apply-left over columns, apply-right over rows) in QR (#300)
- **Sparse triangular solves via level scheduling** — a reusable, **value-agnostic** schedule (`sparse/factorization/level_schedule.hpp`) that stores *positions* into the factor's arrays (not values), so it survives a same-pattern in-place refactorization and reproduces the serial accumulation order exactly. Applied to sparse Cholesky forward + transpose (#301, #302), sparse LU lower/upper (#304), sparse LDLᵀ unit-lower + transpose (#305), and the supernodal LDLᵀ (#306) and supernodal LU (#309) solves
- **BLIS multi-loop GEMM** — the blocked GEMM's ic-only parallelism generalized to a 2D `jc_nt × ic_nt` thread grid: each jc-team's leader packs the shared B panel once and the team splits the ic-blocks, synchronized by a per-team barrier. Scales tall, wide, and square shapes; every C macro-block gets the same FMAs in the same order regardless of grid shape. The per-team barrier keeps a throwing worker in the barrier protocol so a team can never hang, rethrowing after the region joins (#311)
- **Element-wise expression sweeps** — the dense vector/matrix expression-template assignments (`y = a + b`, `C += A + B`, construct-from-expression, `+=`/`-=`) route through a `detail::parallel_ewise` helper; each output element is independent, so contiguous chunking is bit-identical (#312)
- **Encapsulation** — the numeric factor types privatize `L`/`U`/`D` and their coupled solve schedules behind a validating, strongly-exception-safe `set_factor(...)` with read-only accessors, so the schedule can never drift from the factor pattern; `solve()` rejects a missing factor with `std::logic_error` (#305–#309, #307/#308)
- **CI** — `threaded` (GCC+Clang, `MTL5_NUM_THREADS=4`) and `ThreadSanitizer` lanes on push and PRs, plus the design field guide `docs/design/parallelization-patterns-and-pitfalls.md` (#299/#303, #301)

#### Eigenvalue/eigenvector solvers (epic #202)
- **`mtl::eigen`** — general (non-symmetric) eigenvalues **and right eigenvectors**, returned as a structured-bindable `{ eigenvalues, eigenvectors }` (complex), mirroring `eigen_symmetric`. In the in-house path, eigenvalues come from the general QR path and each eigenvector is recovered by **inverse iteration** on `A - lambda_k*I` (partial-pivot complex LU with a pivot floor); cluster-aware Gram-Schmidt deflation yields an **independent basis for repeated eigenvalues**. When LAPACK is available and the type qualifies, `eigen` instead dispatches to `geev` (which returns the eigenvectors directly — see #204). Eigenvectors are unit-norm with a canonical phase (#203)
- **LAPACK `geev` dispatch** for the general eigenproblem — `eigenvalue`/`eigen` route to `sgeev_`/`dgeev_` when `MTL5_HAS_LAPACK` is defined and the matrix is a column-major `dense2D<float/double>` (mirrors the symmetric `syev` dispatch); custom number types and other orientations use the in-house path (#204)
- **Matrix-free iterative eigensolvers** in `mtl::itl` (`include/mtl/itl/eigen/`), operating through the `LinearOperator` concept (`A * x`) so they apply to `dense2D`, `compressed2D`, and user matrix-free operators: `power_iteration` (dominant pair), `lanczos` (symmetric, k extremal Ritz pairs via a tridiagonal projection), `arnoldi` (general, k Ritz pairs via a Hessenberg projection). Each solves the small projected problem with the dense eigensolvers; an `eigen_which` selector picks the wanted end of the spectrum (#205)
- **Sparse eigensolver with shift-invert** in `mtl::sparse` — `sparse_eigs` (largest-magnitude, Arnoldi directly on the sparse operator), `sparse_eigs_shift_invert` (k eigenpairs nearest `sigma` via `(A - sigma*I)^{-1}` applied inside Arnoldi, mapping `lambda = sigma + 1/theta`), and the reusable `shift_invert_operator` (factor once with sparse LU, apply many; tiny pivots perturbed so a shift on an eigenvalue stays solvable) (#206)

- With this, MTL5 covers the core BLAS surface: **L1** dot/nrm2/axpy/scal, **L2** gemv/ger/symv/trmv/trsv, **L3** gemm/trmm/trsm/symm/syrk/syr2k

### Changed
- **The epic #82 acceptance gate now asserts the MEDIAN of the per-size ratios**, with a new `--floor` (default 0.70) that no individual size may fall below. It previously failed if *any* size fell under the threshold — gating on the minimum, the noisiest statistic available. Two runs of the identical protocol on the same idle machine failed at disjoint sets of sizes; the median is reproducible to 0.2 points where per-size values swing up to 6. Raising the iteration count does not help: within-run stddev is already 0.3–2.2%, so the variance is *between* runs, not within them (#327)
- **`run_scaling_297.sh` defaults to `SPARSE_SIZES=100,160`** (was `200,320`, which did not complete — a `T=1` run was killed after 3 h 28 min without finishing its first size). Sparse cost is dominated by the untimed factorization and grows steeply with the grid side: 11 s at 100, 3 m 38 s at 160, 8 m 46 s at 200, *per thread count*. The cost table is recorded next to the default so it is raised deliberately (#321)
- **CI runs when a draft PR is promoted to ready.** `pull_request` declared no `types`, so the default `[opened, synchronize, reopened]` applied and `ready_for_review` fired nothing. ### Fixed
- **`bench_klu` / `bench_superlu` did not compile** — they referenced `blk.L` / `blk.U` on `lu_numeric`, whose members are private (`L_` / `U_`). Nothing caught it because no CI job built the benchmark targets; they had not been compiled since `lu_numeric` was encapsulated. Now use the public `factorL()` / `factorU()` accessors (#319)
- **`bench_sparse`'s 3-D Laplacian grid is clamped.** `g3 = cbrt(g^2)` sized it so its DOF count matched the 2-D case, but `max(8, ...)` bounds `g3` only from *below* despite the comment claiming otherwise. Equal DOF is not equal cost — a 3-D Laplacian has far worse fill growth under Cholesky — so raising the 2-D size implicitly selected an intractable 3-D problem. Clamped to 32; grid side 200 went from *killed after 3 h 28 min* to 8 m 46 s (#322)
- **`mtl::svd` returned all-NaN singular values for ~30% of ordinary symmetric matrices**, and values wrong by up to several hundred percent for many of the rest; `condition_number`, `rcond`, `numerical_rank` and `nullity` all inherited it through `detail::singular_values`. Two independent defects. (a) `householder` formed `sum(x(i)^2)` unscaled and guarded only *exact* zero, so a tiny sigma reached `beta = 2*v0*v0/(sigma + v0*v0)` with both terms flushed to zero (0/0), while `v(i) /= v0` overflowed; `apply_householder_left/right` then evaluated `beta * v(i) * w` as `0 * inf`. Since `qr_factor` stores `v` below the diagonal, the poison spread into the factor. (b) The alternating-QR iteration converged to ~1e-9 and then **corrupted its own answer** — 136% wrong by iteration 1000 on a 10×10 SPD case — while its convergence test (off-diagonal mass / diagonal mass) kept shrinking and so read as converged; `max_iter = 100*max(m,n)` meant the corrupted value was the one returned. Replaced with **one-sided Jacobi**. Verified against LAPACK `dgesvd` over 1800 random matrices: 0 NaN, worst relative deviation 3.0e-15 (#337)
- **`mtl::itl::pc::ilu_0::solve` counted the diagonal in its back-substitution off-diagonal sum**, computing `x(i) = (y(i) - sum_{j>=i} U(i,j)*x(j)) / U(i,i)` — subtracting `U(i,i)*x(i)` and then dividing the difference by that same `U(i,i)`. Wrong for every input: on a diagonal matrix, where ILU(0) is exact, it returned `(b - d*b)/d` instead of `b/d`. The diagonal is now stored only in `u_diag_`, making `u_rows` strictly upper by construction so no consumer can forget to skip it. On a tridiagonal system where the factorization is exact, preconditioned BiCGSTAB now converges in 1 iteration instead of 11 (#323)
- **`mtl::ldlt_bk_factor` produced a wrong solution whenever a pivot interchange occurred**, under `info == 0` — normwise backward error ~1e-1 instead of ~1e-16, in 4560 of 5700 random symmetric matrices. `symmetric_swap` permuted the L columns written by *earlier* steps, putting the stored factor in the "single global P" convention while `ldlt_bk_solve` replays the interchanges one step at a time (as LAPACK's `dsytrs` does); the two agree only when nothing is interchanged, which is why the n=2 and n=3 tests passed. The swap is now restricted to columns `>= k`. The pivot *search* was always correct — `ipiv` matched `dsytrf` before and after — and the stored factor now matches `dsytrf` entry for entry (#335)
- **`mtl::two_norm<Acc>` / `frobenius_norm<Acc>` did not compile for either non-trivial accumulator configuration.** They rounded the accumulator out to the *accumulator type* and took its square root — a no-op for a plain arithmetic accumulator, which is why `two_norm<double>` worked and hid it, but an `fma_accumulator<T>` or a quire for configurations 2 and 3, neither of which has a `sqrt`. Now rounds out to the accumulator's own arithmetic precision via the new `accumulator_round_type` (#324)
- **`mtl::eigenvalue` single-shift QR stalled on strongly non-normal matrices** whose complex eigenvalues need a double-shift (Francis) step — it fell through to reading the diagonal and **silently returned wrong eigenvalues** (e.g. the Forsythe companion matrix returned all shift value, which the old trace-only test accepted). Replaced with the **Francis implicit double-shift QR** (EISPACK `hqr`): real Schur form via 1×1/2×2 block deflation, exceptional shifts to break stagnation, and a `std::runtime_error` on non-convergence instead of a wrong result. Discovered while implementing the eigenvector generator (#203); tightened the Forsythe test to compare the full spectrum (#209)
- AMD/COLAMD minimum-degree garbage-collection compaction mis-restored each element's first entry, corrupting the quotient-graph pointers once fill exhausted the elbow room (e.g. the AᵀA pattern of a 2-D 5-point grid at n ≥ 64); it now follows the CSparse compaction order. Surfaced while validating the supernodal-LU column ordering; regression test added (#189, #191)
- `antisymmetric_tensor::set` wrote out of bounds for diagonal indices (`i == j`) under `NDEBUG`, where the guarding `assert` is compiled out; now a safe no-op (#63)
- Benchmark `native` eigenvalue backend was silently dispatching to LAPACK; it now uses the generic C++ solver so `native` vs `lapack` is a genuine comparison (#78)
